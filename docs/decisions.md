# Decision Log

Why, not just what. Chronological order (matches how the decisions were made), not reverse-chronological. Full problem statement and brief: see local `project-brief.md` (gitignored, not in this repo).

---

## 1. Positioning: investigation copilot, not a monitoring platform

**Decision:** MetricTrace is an investigation copilot for an already-flagged discrepancy. It is not a monitoring or drift-detection platform.

**Reasoning:** Deliberate differentiation from tools like Monte Carlo, Metaplane, and Bigeye, which detect that something is wrong. MetricTrace starts after a discrepancy is already known and explains why it exists. Conflating the two would blur the product's actual scope and invite comparison against a category of tools it isn't competing with.

## 2. Methodology: single-agent baseline before multi-agent

**Decision:** A single-agent baseline (deterministic reconciliation core + one LLM explainer) is built and evaluated before any multi-agent component is added.

**Reasoning:** Establishes a working, measurable system first. Multi-agent complexity is added on top of a proven baseline rather than being the first thing built, so any accuracy gain (or lack of one) from the multi-agent architecture is attributable and not just assumed.

## 3. Architecture core: parallel investigator agents (not gated)

**Decision:** Two parallel investigator agents — a metric-definition specialist and a SQL-lineage specialist — run independently and are merged before reconciliation. This ships regardless of the ablation outcome in decision 5.

**Reasoning:** Justified by problem shape, not by an accuracy test: metric-definition differences and SQL-lineage differences are structurally independent analyses, so running them in parallel and merging matches how the investigation actually decomposes. Not gating this on a benchmark result ensures a real multi-agent story survives even if the ablation in decision 4 fails.

## 4. Architecture ablation: skeptic/verifier agent (gated, may be cut)

**Decision:** Explainer-only vs. explainer + skeptic/verifier agent is the one piece of the architecture allowed to be dropped based on benchmark results, per the thresholds in decision 5.

**Reasoning:** Unlike the parallel investigators (decision 3), the skeptic/verifier's value is an empirical claim — that a second agent checking the first improves accuracy or reduces unsupported claims — so it's the right piece to gate on evidence rather than assume.

## 5. Ablation gate thresholds

**Decision:** The skeptic/verifier ships only if the single-agent baseline fails any of:
- Root-cause accuracy on technical/deterministic scenarios ≥ 80%
- Human-escalation accuracy on ambiguous business-rule scenarios ≥ 90%
- Unsupported-claim rate across all scenarios ≤ 10%

If the baseline clears all three, the skeptic is cut from the shipped architecture.

**Reasoning:** Turns decision 4 into a decision the benchmark can actually make, instead of a subjective call after the fact.

## 6. Open eval-design question: escalation accuracy denominator

**Decision:** Not yet resolved. Must be decided before Build 2 eval code is written: whether human-escalation accuracy (decision 5) is measured only against the true-ambiguous scenario subset, or against the full benchmark.

**Reasoning:** Over-escalation could inflate escalation accuracy while dragging down technical accuracy on borderline cases. The two metrics in decision 5 can fight each other if the denominator isn't pinned down first, so this has to be settled before the eval code — not the benchmark scenarios themselves — makes the choice by default.

## 7. Benchmark sample size and reporting

**Decision:** The benchmark is n=20-30 scenarios. Each threshold in decision 5 is reported as a raw fraction (e.g., 21/25) alongside the percentage in any writeup, never as a bare percentage.

**Reasoning:** The sample is too small for a bare percentage to be self-evidently stable — 80% on n=25 is 20/25, and that difference matters to a reader evaluating the claim.

## 8. Build ordering: freshness/data-quality scenarios moved ahead of the benchmark build

**Decision:** Freshness and data-quality investigation, originally planned as a later addition, was moved ahead of the benchmark-and-eval build.

**Reasoning:** The benchmark and the single-vs-multi-agent gate decision (decisions 4-5) are made once, against the full scenario set including freshness causes. Building freshness scenarios after the benchmark and gate decision were already made would have forced revisiting that decision once freshness scenarios were added — moving it earlier avoids that rework.

## 9. Tech stack

**Decision:** LangGraph for orchestration. ~~Gemini (free tier)~~ **Hugging Face Inference Providers (free tier)** as the LLM, behind a provider-abstraction layer (`llm_client.py`). Pydantic for schema-enforced structured output at every tool/agent boundary. Sqlglot for SQL AST diffing. DuckDB for the scenario data store. Streamlit for the UI, calling the engine directly — FastAPI deliberately deferred to a future-improvements note, not built now. Tenacity for retry/backoff, given the LLM provider's free-tier rate limits.

**Reasoning:** Each choice maps to a specific constraint: LangGraph for the multi-agent orchestration in decisions 3-4; the provider-abstraction layer so the LLM can be swapped without touching agent logic (exercised for real, see the Update below); pydantic structured output so the LLM never gets to freeform its way past a schema boundary; sqlglot and DuckDB as the deterministic-core tools that do the actual computation, per the project's deterministic-core-LLM-at-the-edge convention; Streamlit-direct over a FastAPI layer because no second consumer of the engine exists yet, so the extra layer would be unused abstraction; tenacity because free-tier rate limits make retry/backoff a functional requirement, not an optimization.

**Update (Build 1, Week 2 Day 1 — LLM explainer, PR #39):** Live testing of `llm_client.py` found the configured Gemini API key required prepaid billing credits, which were already exhausted — not a true free tier at all (the "free tier" framing in this decision's original text was wrong for how that key was actually provisioned). Swapped to Hugging Face's Inference Providers API (`huggingface_hub` SDK, model `meta-llama/Llama-3.1-8B-Instruct`, routed to the `Meta-Llama-3.1-8B-Instruct-Turbo` variant via Together), which has a genuine no-billing free tier. This is exactly the swap the provider-abstraction layer was built to absorb: only `src/llm_client.py` and the `google-genai`/`huggingface_hub` dependency line changed — `src/explainer.py` and every downstream caller were untouched. `tenacity`'s rate-limit retry predicate was rewritten against `huggingface_hub.errors.HfHubHTTPError`'s `response.status_code` (was `google.genai.errors.ClientError.code`) — same behavior (retry only a 429, reraise everything else), different exception shape per provider. One further distinction confirmed directly against HF's docs and forum-reported behavior (not assumed): a *rate-limit* hit is a 429 (tenacity retries it), but *monthly credit exhaustion* is a separate 402 Payment Required — non-transient, correctly NOT retried by the existing predicate (retrying a 402 would just waste attempts on an error that cannot resolve itself), and correctly surfaces immediately via `reraise=True`. No code change was needed to get this right; it fell out of the predicate already being narrowly scoped to 429 rather than "any HfHubHTTPError."

**Sustainability check for Build 3's volume (same task, measured not assumed):** Hugging Face's free tier grants $0.10/month in Inference Provider credits per account (per HF's own pricing docs, "subject to change"), separate from and in addition to whatever per-minute/per-day rate limits the routed provider (here, Together, via HF's router) enforces. Rather than assume this is enough for Build 3's 20–30 scenario benchmark, actual per-call cost was measured by running all 7 current fixtures' real explainer prompts through the live API and reading each response's `usage.estimated_cost` field: total cost for 7 real calls was **$0.0001183** (prompt sizes 337–466 tokens, completions 178–258 tokens). Linearly projected, a full 20–30 scenario pass costs roughly **$0.00034–$0.00051** — about 0.3–0.5% of the $0.10 monthly budget, meaning the free tier comfortably supports on the order of 200 full benchmark passes per month at this model/prompt size before hitting the credit wall, not a handful. **Open risk, not fully closed:** this measurement covers only Build 1's single-explainer-call-per-scenario shape; Build 4's multi-agent core (parallel investigators, possible skeptic/verifier) and any Build 3 iteration that re-runs the benchmark repeatedly in one month could plausibly raise per-scenario call count by 3–5x, which still leaves comfortable headroom at these prices but has not itself been measured. Re-check this arithmetic once Build 3's actual scenario count and Build 4's actual per-scenario call count are known, rather than assuming this measurement still holds unchanged.

## 10. Precedence rule: sql_diff's `distinct` finding suppressed in favor of definition_diff's `aggregation` finding

**Decision:** When `sql_diff`'s `distinct` category and `definition_diff`'s `aggregation` field trace to the same underlying COUNT vs. COUNT DISTINCT fact (Case 2), the `distinct` finding is suppressed in favor of the `aggregation` finding. The DISTINCT toggle is a downstream symptom of the aggregation-definition disagreement, not an independent cause.

**Reasoning:** A read-only audit of the 6 scenario fixtures found that Case 2's `distinct` (sql_diff) and `aggregation` (definition_diff) findings both describe one SQL fact — source A uses `COUNT(DISTINCT customer_id)`, source B uses `COUNT(customer_id)` — surfaced twice by two different tools rather than representing two independent causes. Left unresolved, this double-counts the same root cause in reconciliation. This is structurally the same kind of precedence rule as Day 4's self-consistency suppression (a `SelfConsistencyIssue` suppressing the matching cross-source `DefinitionDifference`), applied to a second category pair: one finding is the authoritative account of a fact, the other is a redundant restatement of it from a different angle, and only the authoritative one should reach reconciliation.

**Implementation:** `assemble_structural_and_definitional_evidence(sql_differences, definition_differences)` in `src/self_consistency.py`, with the "same underlying fact" test in `_same_count_distinct_fact` (same file). **This decision was recorded here before any enforcing code existed** — a Day 5, Task 1 verification pass found the rule had been treated as real infrastructure across planning conversations despite having zero implementation anywhere in the codebase; Task 1b (`tests/test_structural_definitional_precedence.py`) built and proved it against a real Case 2 collision and a constructed over-fire case (a DISTINCT toggle paired with an unrelated aggregation-function change) before decision 11's Shapley-averaging engine was allowed to depend on it. Lesson for future decisions in this log: a decision entry describes an intent, not a guarantee that code exists — cross-check the implementation pointer, don't assume one.

## 11. Attribution method: pairwise averaging replaces fixed-order sequential subtraction

**Decision:** For any pair of remaining causes (after Day 4's self-consistency suppression and decision 10's distinct/aggregation suppression) that could plausibly act on overlapping rows, Day 5's reconciliation math computes both isolated counterfactual effects (each cause measured with the other held first at source A's setting, then at source B's setting) and attributes the average of the two as that cause's dollar impact — not a single fixed-order sequential subtraction. This applies uniformly to every remaining pair, without first attempting to detect whether the pair actually overlaps on real rows. Overlap-detection-before-averaging (to skip the extra counterfactual query when two causes are provably independent) is deferred to Build 3, to be revisited only if query cost at 20-30 scenarios makes it worthwhile — not built speculatively now against 6 scenarios where the extra query cost is negligible.

**Reasoning:** Real-execution testing (not static SQL reading) against synthetic row-level data for Case 2 and Case 3 confirmed genuine interaction in both — Case 2's excluded_statuses effect measured 2 under DISTINCT aggregation vs. 3 under non-distinct COUNT (driven by duplicate rows on the status boundary); Case 3's naive additive sum (850.0) missed the true reconciled value (450.0) by exactly 400, one overlap row's amount double-counted because it was excludable by two different mechanisms (date filter on one side, status filter on the other) that sequential subtraction cannot distinguish without either double-counting or dropping it. With exactly two causes per interacting pair, averaging both orderings is the exact Shapley-value solution, not an approximation, so there is no accuracy cost to always applying it. The earlier "definitional differences resolved before structural differences" fixed order (decision pending, chat-only, never committed to this log) is abandoned as empirically unsupported: every confirmed interaction found so far is definitional-vs-definitional, not definitional-vs-structural, so the original rule was never actually tested against a case where it would matter. Scope caveat, stated explicitly to avoid overclaiming: interaction has been confirmed only for definitional-vs-definitional pairs (aggregation-vs-excluded_statuses in Case 2, date_field-vs-excluded_statuses in Case 3). Definitional-vs-structural interaction (e.g., a join-type difference interacting with a definitional filter) remains untested, not ruled out — none of the 6 current fixtures happen to pair a definitional cause with a structural one on overlapping rows. This method should be re-verified, not assumed to generalize, once Build 3 authors scenarios that create that pairing. General n>2 cause interaction (requiring full Shapley averaging across more than two orderings) is also untested and deferred to Build 3 for the same reason — no current fixture has 3+ interacting causes.

## 12. Precedence rule: sql_diff's `date_field` finding suppressed in favor of definition_diff's `date_field` finding

**Decision:** When `sql_diff`'s `date_field` category and `definition_diff`'s `date_field` field trace to the same underlying date-column swap (Case 3: source A uses `order_date`, source B uses `created_at`), the `date_field` SQLStructuralDifference is suppressed in favor of the `date_field` DefinitionDifference. The mechanical structural finding is a downstream restatement of the business-meaning definitional finding, not an independent cause.

**Reasoning — precedence direction, reasoned explicitly rather than assumed symmetric with decision 10:** Decision 10 kept the business-declared `aggregation` finding (`count_distinct` vs. `count`, a human-authored config choice) over the mechanical `distinct` toggle it produces as a byproduct. The same question had to be asked here, not assumed to transfer automatically: does the `date_field` DefinitionDifference carry the same kind of independent, human-authored information the `aggregation` finding did in decision 10, or is it just a second mechanical restatement with extra steps? Checked directly: when both sides declare their `date_field` (the fully-symmetric case with decision 10 — both `source="declared"`, `confidence="high"`), the definitional finding states an intentional analyst choice ("this dashboard reports by order date, that one by record-creation date") — exactly the kind of business-meaning explanation decision 10 judged more valuable to a human reader than a bare structural fact. Case 3 itself is the asymmetric case — B has no declared definition, so its `date_field` value is inferred straight from the same SQL `sql_diff` already parsed, and the field's overall `source`/`confidence` is capped to `"inferred"`/`"medium"` by `diff_definitions`'s weakest-link rule (`src/definition_diff.py`). The suppression rule is nonetheless applied uniformly regardless of confidence, matching decision 10's own rule (which also does not gate on confidence) and keeping one consistent rule per category pair rather than two. Caveat, stated explicitly rather than left implicit: this has been proven only at `confidence="medium"` (Case 3, and the constructed over-fire case below); a `confidence="low"` inferred `date_field` (ambiguous SQL, multiple or zero date-like columns) suppressing an always-mechanically-correct structural finding is untested and could plausibly warrant the opposite call, since the structural finding cannot be wrong about what the SQL literally does, while a low-confidence guess can. Flagged for the Build 3 audit below, not resolved here.

**Reasoning — dollar-value handling, checked against the Case 7 lesson rather than assumed safe:** Day 7 Part A (this same build day) found that suppressing a finding can silently discard a real, separate dollar contribution if the suppressed finding represented an independent, additional correction step (Case 7: self-consistency correction, then a further, separate cross-source correction — two sequential deltas that had to be summed). This collision was checked against that exact risk and found NOT to have it: unlike Case 7's two sequential corrections, `sql_diff`'s `date_field` finding and `definition_diff`'s `date_field` finding, when they trace to the same fact, describe the *same single* SQL mutation (swap the date column) — not two chained ones. `construct_corrected_query` applied once, using the surviving `DefinitionDifference`, already performs the complete correction; there is no second, independent dollar-bearing step to fold in. Verified directly: Case 3's `ReconciliationLineItem` for `date_field`, computed the normal way after suppression, reproduces exactly the same dollar figure (-400.0, negated from Day 5 Task 2's committed +400.0) that was already proven correct before this decision existed — nothing is missing.

**Pattern note — third occurrence of the same class of gap:** This is the third time this project has discovered two independent tools producing findings that trace to one underlying fact, with no suppression rule reconciling them, only after building further downstream logic that depended on the evidence being non-redundant: Day 4's self-consistency-vs-cross-source collision (a `SelfConsistencyIssue` and a `DefinitionDifference` both describing one source's own field), decision 10's `distinct`-vs-`aggregation` collision, and now this `date_field`-vs-`date_field` collision, all found by different downstream work (Day 4 Part 2's own precedence rule, a Case 2 audit before decision 10's engine was trusted, and Day 7 Task 1's `ReconciliationLineItem` assembly, respectively) rather than by deliberately searching for them. **Forward note:** a systematic audit of every `SQLStructuralDifference` category against every `DefinitionDifference` field for this same risk should happen before Build 3's larger scenario set is authored, rather than continuing to discover these one fixture at a time — the categories not yet audited this way are `filter`, `distinct` (audited, decision 10), `join_type`, `aggregation` (audited, decision 10), `date_field` (audited, this decision), `grouping`, and `other`.

**Implementation:** `_same_date_field_fact` and the extended `assemble_structural_and_definitional_evidence`, both in `src/self_consistency.py` — the same function decision 10 lives in, extended rather than duplicated, since both are "an sql_diff structural finding collides with a definition_diff definitional finding" instances of one general shape. "Same underlying fact" is defined precisely, mirroring `_same_count_distinct_fact`'s precision standard: not mere category co-presence, but a side-matched exact equality between the structural finding's own referenced columns (parsed from its snippet text via sqlglot, requiring exactly one unambiguous column per side) and the definitional finding's own declared/inferred values. Proven against the real Case 3 collision (`test_case_3_date_field_suppressed_excluded_statuses_survives`) and a constructed over-fire case where a structural finding references two ambiguous date columns on one side while the definitional finding differs on a completely unrelated column pair (`test_does_not_over_fire_on_unrelated_date_field_findings`), both in `tests/test_structural_definitional_precedence.py` — built and proven before being relied upon, unlike decision 10's own history.

## 13. `known_gap` and seed-execution dollar figures were not scale-calibrated for Cases 1–5 — discovered, then resolved

**Decision (original, Day 7 Task 2):** Not a fix at the time — recorded as a known, named gap rather than silently smoothed over, per this project's own standing rule for a fixture that fails a check without a code bug behind it. `assemble_investigation_evidence`'s `unexplained_residual` (Build 1, Day 7, Task 2) was large for Cases 1–4 (91–99.9% of `known_gap` unexplained) even though every cause found in those scenarios was correctly identified and correctly signed (same direction as `known_gap` in every case, verified explicitly). Not treated as a defect to fix in that task.

**Resolution (Build 1, Day 7, Task 3):** Fixed. `reported_value_a`, `reported_value_b`, and `known_gap` for Cases 1–4 (`tests/fixtures/scenarios.py`) were replaced with values derived from executing each scenario's actual as-written SQL against its actual seed data (`{seed_table}_a.duckdb`/`{seed_table}_b.duckdb`), matching Case 7's original standard exactly. Case 5 and Case 6 were checked the same way and found to already be correctly calibrated — their executed values matched their existing hand-typed figures exactly, so no numbers changed there, but the check was performed, not skipped. Case 7 was left untouched (already calibrated since the Day 4 close-out). No SQL, declared definitions, or seed data were altered — only the three top-level `Scenario` fields. This is now the uniform convention for all 7 fixtures, and applies to any fixture added later: a scenario's `reported_value_a`/`reported_value_b`/`known_gap` must be derived from real execution of its own SQL against its own seed data, never hand-typed independently of it.

**Result:** Every one of Cases 1–4 now reconciles to an exact 0.0 residual (0.0% of `known_gap`), not merely "near zero" — the single or paired cause found in each case fully and exactly accounts for the recalibrated gap. This confirms the reconciliation math itself (Shapley pairing, self-consistency folding, decision 10/12 suppression, sign convention) was correct all along; only the fixture calibration was off. Case 5's residual remains 100% of `known_gap` (3800.0), unchanged and correct by design — no cause exists for it to find. Case 6 remains 0/0, unchanged. Full before/after figures and the recalibrated 7-fixture table are recorded in the Day 7 Task 3 session report, not duplicated here.

**Reasoning (why the gap existed):** `Scenario.known_gap`'s own docstring (`src/scenario.py`, written back in Build 1 Day 1 Part 2) already stated the two numbers were never *required* to match in magnitude: "known_gap is the hand-authored, independently-asserted expected value — it is not derived from executing against seed_table." Cases 1–4's `reported_value_a`/`reported_value_b` had been authored at a realistic dashboard scale (hundreds of thousands), while their seed data was built at a much smaller, independently-chosen scale for tractable hand-verification (tens to low thousands) — the two were never calibrated to reconcile against each other, even though nothing in the schema forbade doing so. Case 7 was the sole exception at the time, and the only non-trivial case with a near-zero residual before this resolution: its `reported_value_a`/`reported_value_b` were deliberately set equal to real seed-execution figures (300.0/100.0) when the fixture was built during the Day 4 close-out, specifically so the precedence rule could be proven against a real, checkable number. Cases 1–5 had never been given that same treatment — Task 3 gave it to them.

This was a genuinely new finding when Task 2 surfaced it, not a rediscovery of an already-flagged item: every prior verification in this project (Day 5's Shapley proofs, Day 6's self-consistency dollar figures, Day 7 Task 1's line-item assembly) compared execution results against *other* execution results (hand-verified SQL variants) or checked *direction* against `known_gap`, never magnitude-reconciled against it directly. Task 2 was the first point in the project where that direct comparison happened, which is why the gap surfaced only then — and why Task 3 could fix it immediately once named, rather than requiring further investigation.

**Consequence, stated plainly (post-resolution):** the sum-equals-`known_gap` check (`total_dollar_impact + unexplained_residual == known_gap`) holds exactly for all 7 fixtures, and remains an algebraic identity of how `unexplained_residual` is *defined* (the same caveat decision 11's Shapley sum-check already carries) regardless of calibration — it alone never proved the residual was small. What changed is the separate, meaningful claim: whether the residual is actually small now holds for Cases 1, 2, 3, 4, and 7 (all exactly 0.0%), in addition to Case 5 (100%, correctly, by design — no cause exists to find). No fixture is left in the "large residual with no explanation" state this decision originally described.

**Forward note (superseded by the resolution above, kept for history):** the original entry recommended calibrating future fixtures the way Case 7 was, without retroactively touching Cases 1–5 due to the cost of rescaling already-verified numbers. Task 3 concluded that cost was worth paying — every downstream committed test that depended on the old figures was re-run and updated deliberately (not force-fit), confirming the reconciliation logic itself needed no changes. The recommendation that stands going forward: any fixture added in Build 3 or later must have `reported_value_a`/`reported_value_b`/`known_gap` derived from real execution against its own seed data from the moment it's authored, per the Resolution paragraph above — not deferred and revisited later the way Cases 1–6 were.

## 14. LLM explainer grounding defects, observed and characterized for Build 3's unsupported-claim-rate checker (not fixed — deliberately left as test targets)

**Decision:** Two real, observed defects in the Hugging Face explainer's prose (Build 1, Week 2 Day 1, PR #39's live 7-fixture verification) are recorded here with enough reproduction detail that whoever builds Build 3's unsupported-claim-rate checker can write a targeted test for each pattern, rather than relying on a vague "check for hallucination" mandate. Per this project's own standing rule (see decision 10's lesson), a finding recorded without enough specificity to act on is close to not being recorded at all.

**Defect 1 — sign-dropping on a correctly-sourced dollar figure (Case 2, `case_02_multi_cause`):** `InvestigationEvidence.reconciliation` for this fixture contains a line item with `cause="aggregation: source_a declares 'count_distinct', source_b declares 'count'"` and `dollar_impact=-1.5` exactly (confirmed via `assemble_investigation_evidence(CASE_2_MULTI_CAUSE)`, not assumed). The prompt built by `_format_evidence_prompt` (`src/explainer.py`) renders this correctly-signed, as `dollar_impact=-1.50` (the `:+.2f` format spec). The live model response narrated it as: *"the difference in aggregation methods, with source A using 'count_distinct' and source B using 'count', has a dollar impact of $1.50"* — the magnitude is exactly right, the sign is silently dropped. This is not a fabricated cause or a fabricated number; it is a real number stripped of a real, given sign. **Test pattern for Build 3:** for every `ReconciliationLineItem` with a negative `dollar_impact`, check whether the explainer's prose states that figure's magnitude without an accompanying negative/"reduces"/"offsets"/"negative impact of"-type qualifier — a magnitude-only mention of a negative figure is the specific shape of this defect, distinct from a magnitude mismatch (wrong number entirely) or a fabricated cause (a number/cause absent from evidence).

**Defect 2 — narrating an empty category as a "cause that does not exist" (Case 4, `case_04_governance_drift`):** This fixture's `definition_differences` and `sql_differences` are both empty lists (self-consistency-only scenario, by design — the precedence rule suppresses the one real cross-source finding into `self_consistency_issues` instead). `_format_evidence_prompt` renders each empty category as a plain `"- None."` line, exactly as it does for every other fixture with an empty category (Cases 1, 3, 5, 6, 7 all have at least one empty category rendered the same way, all without triggering this). The live model response for Case 4 specifically narrated these as invented, then-negated causes: *"We have also identified a reconciled cause that is a result of definitional differences between source A and source B. However, this cause does not exist, and the dollar impact is zero... Another reconciled cause is related to SQL structural differences between the two sources. However, this cause also does not exist, and the dollar impact is zero."* No false cause or number reaches a final claim (each is explicitly negated in the same sentence), but the narrative structure invents a "candidate cause" only to retract it — confusing, and a warning sign for how this class of model handles an all-empty section next to a populated one. **Test pattern for Build 3:** for a fixture where at least one evidence category is empty and at least one is populated, check whether the prose introduces language implying a cause exists in the empty category (e.g. "a[nother] reconciled cause... however, it does not exist" or equivalent hedge-then-retract phrasing) rather than simply omitting or plainly stating "none" for that category — the retraction saves it from being a false claim, but the pattern itself (inventing a candidate to negate) is what to flag, not just bare factual accuracy of the final sentence.

**What was deliberately NOT done:** neither defect was prompt-engineered away. Per this task's own instruction, a defect observed on Cases 5/6 (the two fabrication-risk cases) would have been reportable as a finding about the model's behavior rather than silently patched — the same standard applies here: these are real, current behaviors of `meta-llama/Llama-3.1-8B-Instruct` against this project's current prompt (`_format_evidence_prompt`), not resolved by this decision, and a future prompt-wording change or model swap should be re-verified against both patterns rather than assumed to have fixed them.

**Scope note:** both defects were observed on a single live run per fixture; LLM output is non-deterministic, so a re-run may phrase things differently even against the same evidence and prompt. What is being recorded is the *category* of defect (sign-dropping on real figures; hedge-then-retract narration of empty categories), confirmed present at least once each, not a claim that either reproduces identically on every call.

## 15. `Scenario.seed_table`'s meaning overloaded for freshness scenarios, rather than introducing two clean new fields

**Decision:** Build 2, Day 1 needed to represent a freshness-testing scenario's two required snapshots per side (a "stale/as-delivered" version and a "complete" counterfactual). Rather than add two new fields and leave `seed_table` untouched, `seed_table`'s existing meaning was reinterpreted for freshness scenarios specifically: it now names the "stale/as-delivered" snapshot when a freshness cause is being tested, while a new field, `freshness_complete_seed_table: str | None = None`, names the second, "complete" counterfactual pair. For every non-freshness scenario (all 7 Build 1 fixtures), `seed_table` means exactly what it always meant — this is a conditional second meaning layered onto one field for a subset of scenarios, not a renaming.

**Reasoning:** This session's own brief suggested a single base name with a four-way suffix chain instead (`{seed_table}_a_complete.duckdb`/`{seed_table}_a_stale.duckdb`/`..._b_complete...`/`..._b_stale...`), which would have kept `seed_table` a single unambiguous concept and made the stale/complete distinction a pure suffix rather than a field-level reinterpretation. The reinterpretation approach was chosen instead for two reasons: (1) it requires zero changes to any already-committed code that resolves `seed_table` (`scripts/build_seed_data.py`, `reconciliation_assembly.py`, `self_consistency.py` all keep resolving it exactly as they do today, freshness fixture or not); (2) it avoids a physical duplicate "_stale" file that would just be a second copy of data `seed_table`'s own per-side files already provide — the "stale" snapshot for a freshness fixture is not new data, it's the same data every other fixture's `seed_table` already names.

**The tradeoff, stated plainly:** `seed_table` is now a field whose meaning depends on whether `freshness_complete_seed_table` is set on the same `Scenario` — a reader (or a future Code session) who trusts `seed_table`'s surface meaning ("the scenario's backing data") without checking the sibling field can be wrong about what it represents for a freshness fixture specifically. This is the same shape of risk decision 13 named directly: an undocumented dual-meaning field is exactly what caused the `known_gap`/seed-execution calibration confusion there. The mitigation taken here, to avoid repeating that mistake: `seed_table`'s own docstring (`src/scenario.py`) was updated in the same commit, not left as-is — it now states explicitly that for a freshness scenario, `seed_table` specifically names the stale/as-delivered snapshot, and points to `freshness_complete_seed_table` for the complete counterfactual. The dual meaning is documented at the point of overload, not left implicit.

**Recorded here, not just in the docstring, because of decision 10's own lesson reversed:** decision 10 warned that "a decision entry describes an intent, not a guarantee that code exists." The reverse failure is just as real -- a design choice documented only in a docstring, with no entry in this log, is invisible to a future audit or a reviewer of the public repo who checks `docs/decisions.md` for architectural judgment calls without reading every module's docstrings first. This entry exists so that check finds something.

**Consequence for Build 2, Day 2+:** whoever writes the freshness-detection logic, the seed-data build script, and the first freshness fixture must resolve `seed_table` as the stale snapshot and `freshness_complete_seed_table` as the complete one -- not assume `seed_table` alone is sufficient, and not assume the two fields are independent of each other's meaning. If a future session finds this overload confusing in practice (e.g. it becomes hard to tell, reading a fixture alone, whether `seed_table` is being used in its freshness sense or its plain sense), splitting into two always-populated fields remains available as a follow-up refactor -- not done now, since no fixture yet exists to prove the confusion is real rather than hypothetical.

## 16. `late_arriving_data` deferred to Build 3, not built in Build 2

**Decision:** `late_arriving_data` (the fourth `DataQualityIssue` category, `src/schema.py`) is deferred to Build 3. It will not be built in Build 2, Day 5 or any remaining Build 2 session. Build 2 ships with exactly three working checks -- `check_stale_extract`, `check_missing_partition` (Day 3, `_check_completeness`), and `check_referential_integrity` (Day 4, `_orphan_count`) -- not four. This is a scope decision made deliberately, not a timeline slip: the category isn't late, it's moved.

**Reasoning:** `late_arriving_data` was assumed, when the `DataQualityIssue.category` Literal was written (Build 2, Day 1), to be buildable the same mechanical way `missing_partition` extended `stale_extract` in Day 3 -- reuse an existing detection primitive under a new category label, distinguished only by fixture construction. That assumption was tested directly in this session's own planning discussion, with a precise question: is `late_arriving_data` honestly distinct from `stale_extract`, or would it just be a third row-count check wearing a third label? The test posed was: does re-running the SAME query, with the SAME extraction/query logic, at a LATER point in time, against data that has since fully arrived, produce the complete result -- i.e. is this genuinely about *when* rows arrived, not *whether* a different snapshot or a differently-scoped query is needed to see them? If yes, that is real lateness, and detecting it needs a mechanism `_check_completeness`/`_orphan_count` do not have: a per-row EVENT-TIME column (when the row's underlying business event happened) versus an INGESTION-TIME column (when the row actually landed in the table), plus a calibrated cutoff distinguishing "arrived late but did arrive" from "still missing." If no -- if the only way to see the complete data is a different snapshot file or a structurally different query -- then whatever that fixture is testing is `stale_extract` (or `missing_partition`) under a mislabeled name, not a new category at all.

**This test was posed and never passed.** No fixture, real or hypothetical, was constructed this session that cleanly demonstrates the "yes" branch using only this project's existing seed-data conventions (a fixed DuckDB file per side, built once by `scripts/build_seed_data.py`, with no notion of "current wall-clock time" or "a query re-run later"). Every attempt to sketch one either collapsed into a second `stale_extract`-shaped snapshot pair (the "no" branch) or required inventing simulated time-passage machinery (an explicit "as-of" parameter threaded through the seed-data build and the check function) that is a genuinely new mechanism, not a documentation exercise -- exactly the kind of scope growth this project's own "minimum code that solves the problem" convention exists to catch before it's built speculatively.

**What a future Build 3 session must resolve before building this category:**
1. A schema decision: does `late_arriving_data` need new fixture-level fields (an event-time column distinct from the ingestion/extraction time already implicit in `seed_table`, and something representing "the query's as-of time") added to the seed-data shape, or can it reuse `Scenario.freshness_complete_seed_table`'s existing stale/complete pairing by treating "late" rows as present in `complete` and absent from a *third*, genuinely time-gated snapshot? This has not been decided -- both are plausible, neither has been tried.
2. A worked fixture that actually passes the test above: construct it FIRST, prove it is not secretly `stale_extract`/`missing_partition` in disguise, before writing `check_late_arriving_data` -- mirroring how Day 4 confirmed a real fact/dimension relationship existed before writing `check_referential_integrity`, not the reverse order.
3. Re-audit `_CONFIDENCE`'s fixed `"high"` constant (`src/data_quality.py`) against this category specifically -- its own comment already flags that `late_arriving_data`/`referential_integrity` "may have a genuine reason to vary confidence" unlike the row-count checks' mechanical certainty; `referential_integrity` turned out not to need this (an orphan-row count is just as mechanically exact as a row-count diff), but `late_arriving_data`'s cutoff-based judgment call plausibly does, and this has not been re-examined since that comment was written speculatively in Day 2.

**Pattern note -- this is the third item riding into Build 3 under the same shape ("discovered mid-build, needed a design pass Build 2 couldn't absorb"), not three unrelated slips:** decision 12's own forward note (a systematic audit of every `SQLStructuralDifference` category against every `DefinitionDifference` field for cross-tool collisions) and decision 11's own scope caveat (n>2 cause interaction, and definitional-vs-structural pair interaction, both untested by the current fixture set) were each deferred the same way -- a real gap, named explicitly rather than silently assumed safe, carried forward with a stated reason rather than quietly dropped. `late_arriving_data`'s deferral joins that same list. A future session auditing "what did Build 2 actually ship versus what the Build Skeleton originally scoped" should expect exactly these three gaps, not be surprised by any of them.

## 17. `ReconciliationLineItem` and `DataQualityIssue` dollar figures can restate the same fact -- a legibility risk, not a code defect

**Decision:** `DataQualityIssue.dollar_impact` figures are never summed against, or cross-referenced with, `ReconciliationLineItem.dollar_impact` figures anywhere in this codebase -- `data_quality_issues` remains additive-evidence-only (Build 2, Day 5's locked decision). This decision does not change that arithmetic boundary; it records a risk that boundary does not, by itself, fully close: the two lists can describe the *same* underlying dollar delta via two independent computation paths, with nothing in the schema or the assembled `InvestigationEvidence` object stating that to a reader.

**Reasoning, grounded in a real proof, not a hypothetical:** Build 3, Day 1, Part 2 built `CASE_12_JOIN_ORPHAN_COLLISION` specifically to test overlap #7 (`sql_diff`'s `join_type` category vs. `check_referential_integrity`) and Part 4 ran it through `assemble_investigation_evidence` directly. The result, confirmed by execution: `reconciliation` contains one `ReconciliationLineItem` for the `join_type` correction, `dollar_impact=300.0`; `data_quality_issues` separately contains one `DataQualityIssue` for the referential-integrity orphan, `dollar_impact=300.0`. Both figures are numerically identical because both are measuring the exact same correction (excluding the one orphan row) via two independent code paths (`single_cause_attribution` applied to a join-type correction vs. the same function applied to an FK-filter correction) that happen to converge on the same delta. Summing them ($300 + $300 = $600) would double Case 12's real `known_gap` of $300. **`assemble_investigation_evidence`'s own math is unaffected by this** -- `unexplained_residual` for Case 12 is exactly `0.0`, computed entirely from `reconciliation`'s single line item, with `data_quality_issues` never entering that arithmetic at all (proven directly, not assumed, in Part 4). The risk is entirely on the READING side: a human, a report, or a future explainer prompt that treats `reconciliation` and `data_quality_issues` as two independent lists of causes to add together would be wrong, and nothing today would stop that mistake.

**Mitigation, scoped deliberately narrow:** a one-sentence caveat added to `InvestigationEvidence`'s own docstring (`src/schema.py`) stating that a `data_quality_issues` entry's dollar figure may restate a cause already counted in `reconciliation`, and must never be summed against it by a future reader, report, or explainer prompt. This is the ONLY code change this decision makes. A machine-readable pairing mechanism (e.g. a `related_finding_note` field cross-linking the two lists) was explicitly considered and rejected as speculative infrastructure for a risk that is currently a reading hazard, not a proven need with a concrete consumer -- if a future build genuinely needs to detect this programmatically (e.g. to drive a real suppression rule the way decisions 10/12 did for `sql_diff`/`definition_diff` collisions), that is new, separately-scoped work, not something this docstring caveat should grow into on its own.

**Forward note, load-bearing for whoever builds it:** `src/explainer.py` still does not render `data_quality_issues` in its prompt (Build 2, Day 1's original deferral, still standing as of this entry). This caveat is inert today because of that deferral alone -- the moment `data_quality_issues` rendering is added, this decision's mitigation becomes load-bearing, and whoever does that work must read this entry first, not discover the double-narration risk fresh the way Part 2/4 did for Case 12.

## 18. Filter/excluded_statuses suppression rule -- confidence-gated, reverse precedence direction from decisions 10/12

**Decision:** When `sql_diff`'s `filter` category and `definition_diff`'s `excluded_statuses` field trace to the same status column, AND the `excluded_statuses` `DefinitionDifference`'s confidence is EXACTLY `"low"`, the `excluded_statuses` finding is suppressed and the `filter` finding survives. Scoped deliberately narrow to `confidence="low"` only -- a `"medium"`/`"high"`-confidence `excluded_statuses` finding colliding with a `filter` finding is explicitly NOT handled by this rule.

**Reasoning:** This is the third occurrence of the "two tools trace to the same fact" pattern (after decision 10's `distinct`/`aggregation` collision and decision 12's `date_field`/`date_field` collision), but resolved in the OPPOSITE direction on purpose, not by oversight. Decisions 10 and 12 both kept the business-declared/inferred DEFINITIONAL finding over the mechanical structural one, reasoning that a human-authored config choice (or its inferred equivalent) carries more meaning than a bare structural fact -- and that precedent held regardless of the definitional finding's confidence level. This rule inverts that: `filter`'s presence/absence is mechanically certain (a `COUNT(*)`-grade fact, the same certainty class `SQLStructuralDifference` findings already carry), while a `confidence="low"` `excluded_statuses` value is, by `_infer_excluded_statuses`'s own documented contract, a guess made when zero or multiple status predicates were found -- it carries no more certainty than the mechanical fact it collides with, so there is nothing lost by keeping only the mechanical one. This is decision 12's own previously-unresolved caveat -- "a `confidence="low"` inferred `date_field` suppressing an always-mechanically-correct structural finding is untested and could plausibly warrant the opposite call" -- now actually tested, for the analogous `excluded_statuses` case, and found to warrant exactly that opposite call.

**Proven, not asserted:** built and tested against the real Case 13 collision (Build 3, Day 1, Part 2/6) and two required over-fire cases, the same standard decisions 10/12 were each held to before being trusted: a `confidence="medium"`/`"high"` `excluded_statuses` finding colliding with a filter finding does NOT suppress (proving the confidence gate actually gates); a filter finding on an unrelated (non-status) column paired with a genuine low-confidence `excluded_statuses` finding does NOT suppress (proving the "same fact" check is a real column-identity check, not mere category co-presence).

**Explicit scope boundary, named as an open item, not solved by extrapolation:** what happens when a `confidence="medium"`/`"high"` `excluded_statuses` finding collides with a `filter` finding on the same column is undecided. It is tempting to assume the same reversed-direction logic should simply not apply there (since a medium/high-confidence value is presumably "real," the definitional finding should presumably win the way decisions 10/12's own findings did) -- but that has not been tested, and this decision deliberately does not extend to cover it. `assemble_structural_and_definitional_evidence`'s implementation matches this exactly: both findings survive untouched whenever `excluded_statuses`' confidence is anything other than `"low"`, per its own over-fire test.

**Implementation:** `_same_filter_exclusion_fact` and the extended `assemble_structural_and_definitional_evidence`, both in `src/self_consistency.py` -- the same function decisions 10/12 already live in, extended a third time rather than duplicated, matching the file's own established pattern. Unlike `_same_date_field_fact`, there is no stored "which column" value to compare on the definitional side (`_infer_excluded_statuses` is hardcoded to the bare column `"status"`, with no per-instance column identity on a `DefinitionDifference`) -- the column check is necessarily one-sided, reading whichever of the `filter` finding's own two snippets actually parses (`_diff_filters` is presence-only, so exactly one side has a real predicate).
