# Decision Log

Why, not just what. Chronological order (matches how the decisions were made), not reverse-chronological. Full problem statement and brief: see local `project-brief.md` (gitignored, not in this repo).

---

## 1. Positioning: investigation copilot, not a monitoring platform

**Decision:** MetricTrace is an investigation copilot for an already-flagged discrepancy. It is not a monitoring or drift-detection platform.

**Reasoning:** Deliberate differentiation from tools like Monte Carlo, Metaplane, and Bigeye, which detect that something is wrong. MetricTrace starts after a discrepancy is already known and explains why it exists. Conflating the two would blur the product's actual scope and invite comparison against a category of tools it isn't competing with.

## 2. Methodology: single-agent baseline before multi-agent

**Decision:** A single-agent baseline (deterministic reconciliation core + one LLM explainer) is built and evaluated before any multi-agent component is added.

**Reasoning:** Establishes a working, measurable system first. Multi-agent complexity is added on top of a proven baseline rather than being the first thing built, so any accuracy gain (or lack of one) from the multi-agent architecture is attributable and not just assumed.

## 3. Architecture core: parallel investigator agents (not gated)

**Decision:** Two parallel investigator agents — a metric-definition specialist and a SQL-lineage specialist — run independently and are merged before reconciliation. This ships regardless of the ablation outcome in decision 5.

**Reasoning:** Justified by problem shape, not by an accuracy test: metric-definition differences and SQL-lineage differences are structurally independent analyses, so running them in parallel and merging matches how the investigation actually decomposes. Not gating this on a benchmark result ensures a real multi-agent story survives even if the ablation in decision 4 fails.

## 4. Architecture ablation: skeptic/verifier agent (gated, may be cut)

**Decision:** Explainer-only vs. explainer + skeptic/verifier agent is the one piece of the architecture allowed to be dropped based on benchmark results, per the thresholds in decision 5.

**Reasoning:** Unlike the parallel investigators (decision 3), the skeptic/verifier's value is an empirical claim — that a second agent checking the first improves accuracy or reduces unsupported claims — so it's the right piece to gate on evidence rather than assume.

## 5. Ablation gate thresholds

**Decision:** The skeptic/verifier ships only if the single-agent baseline fails any of:
- Root-cause accuracy on technical/deterministic scenarios ≥ 80%
- Human-escalation accuracy on ambiguous business-rule scenarios ≥ 90%
- Unsupported-claim rate across all scenarios ≤ 10%

If the baseline clears all three, the skeptic is cut from the shipped architecture.

**Reasoning:** Turns decision 4 into a decision the benchmark can actually make, instead of a subjective call after the fact.

**Cross-reference:** decision 6 splits the second threshold above into two separate metrics (escalation recall and false-escalation rate) — the gate is now four-way, not three. See decision 6.

## 6. Escalation accuracy resolved: split into escalation recall and false-escalation rate

**Decision:** The single "human-escalation accuracy" metric proposed in decision 5 is replaced by two separate metrics:
- **Escalation recall** — ambiguous scenarios correctly escalated ÷ total ambiguous scenarios. Threshold ≥ 90%.
- **False-escalation rate** — non-ambiguous scenarios wrongly escalated. Reported as a raw count, not a percentage: ≤ 2 out of 15 non-ambiguous scenarios.

**What counts as "escalated":** the system must give one clear, unmistakable statement that no answer is being provided and a person should review it instead. A hedged or partially-confident answer does not count as escalating under any circumstance — it is scored as a regular answer, with no partial credit in either direction.

**Benchmark composition:** a starting target of 10 ambiguous / 15 non-ambiguous scenarios out of 25 total. This is a target, not a hard requirement — if genuinely ambiguous scenarios prove harder to construct convincingly than technical ones during authoring, the split may be revised. Any such revision must be logged as its own follow-up note here, not silently drifted into.

**Reasoning:** The original single-denominator framing (measuring escalation accuracy only against the ambiguous subset) had a real gaming hole: a system that escalates every scenario, ambiguous or not, would score perfectly on that metric alone, since over-escalation on clear-cut scenarios is invisible to a metric that only ever looks at the ambiguous ones. Splitting into two metrics makes over-escalation visible and separately penalized instead of hiding inside a single number. The false-escalation rate is reported as a raw count rather than a percentage because 10% of a 15-scenario subset doesn't divide into a whole number, and expressing it as "10%" would overstate the precision a sample this small can support — the same problem decision 7 already names for the full benchmark's percentages, applied here to a subset even smaller than the full 20-30.

**Consequence for decision 5:** the ablation gate now checks four conditions instead of three — root-cause accuracy ≥ 80%, escalation recall ≥ 90%, false-escalation count ≤ 2/15, unsupported-claim rate ≤ 10%. All four must clear for the skeptic/verifier to be cut from the shipped architecture; failing any one of the four means the skeptic ships. Decision 5's own three-condition text is left as written, not rewritten, since it records the thresholds as originally proposed — this decision is what supersedes the second one.

## 7. Benchmark sample size and reporting

**Decision:** The benchmark is n=20-30 scenarios. Each threshold in decision 5 is reported as a raw fraction (e.g., 21/25) alongside the percentage in any writeup, never as a bare percentage.

**Reasoning:** The sample is too small for a bare percentage to be self-evidently stable — 80% on n=25 is 20/25, and that difference matters to a reader evaluating the claim.

## 8. Build ordering: freshness/data-quality scenarios moved ahead of the benchmark build

**Decision:** Freshness and data-quality investigation, originally planned as a later addition, was moved ahead of the benchmark-and-eval build.

**Reasoning:** The benchmark and the single-vs-multi-agent gate decision (decisions 4-5) are made once, against the full scenario set including freshness causes. Building freshness scenarios after the benchmark and gate decision were already made would have forced revisiting that decision once freshness scenarios were added — moving it earlier avoids that rework.

## 9. Tech stack

**Decision:** LangGraph for orchestration. ~~Gemini (free tier)~~ **Hugging Face Inference Providers (free tier)** as the LLM, behind a provider-abstraction layer (`llm_client.py`). Pydantic for schema-enforced structured output at every tool/agent boundary. Sqlglot for SQL AST diffing. DuckDB for the scenario data store. Streamlit for the UI, calling the engine directly — FastAPI deliberately deferred to a future-improvements note, not built now. Tenacity for retry/backoff, given the LLM provider's free-tier rate limits.

**Reasoning:** Each choice maps to a specific constraint: LangGraph for the multi-agent orchestration in decisions 3-4; the provider-abstraction layer so the LLM can be swapped without touching agent logic (exercised for real, see the Update below); pydantic structured output so the LLM never gets to freeform its way past a schema boundary; sqlglot and DuckDB as the deterministic-core tools that do the actual computation, per the project's deterministic-core-LLM-at-the-edge convention; Streamlit-direct over a FastAPI layer because no second consumer of the engine exists yet, so the extra layer would be unused abstraction; tenacity because free-tier rate limits make retry/backoff a functional requirement, not an optimization.

**Update (Build 1, Week 2 Day 1 — LLM explainer, PR #39):** Live testing of `llm_client.py` found the configured Gemini API key required prepaid billing credits, which were already exhausted — not a true free tier at all (the "free tier" framing in this decision's original text was wrong for how that key was actually provisioned). Swapped to Hugging Face's Inference Providers API (`huggingface_hub` SDK, model `meta-llama/Llama-3.1-8B-Instruct`, routed to the `Meta-Llama-3.1-8B-Instruct-Turbo` variant via Together), which has a genuine no-billing free tier. This is exactly the swap the provider-abstraction layer was built to absorb: only `src/llm_client.py` and the `google-genai`/`huggingface_hub` dependency line changed — `src/explainer.py` and every downstream caller were untouched. `tenacity`'s rate-limit retry predicate was rewritten against `huggingface_hub.errors.HfHubHTTPError`'s `response.status_code` (was `google.genai.errors.ClientError.code`) — same behavior (retry only a 429, reraise everything else), different exception shape per provider. One further distinction confirmed directly against HF's docs and forum-reported behavior (not assumed): a *rate-limit* hit is a 429 (tenacity retries it), but *monthly credit exhaustion* is a separate 402 Payment Required — non-transient, correctly NOT retried by the existing predicate (retrying a 402 would just waste attempts on an error that cannot resolve itself), and correctly surfaces immediately via `reraise=True`. No code change was needed to get this right; it fell out of the predicate already being narrowly scoped to 429 rather than "any HfHubHTTPError."

**Sustainability check for Build 3's volume (same task, measured not assumed):** Hugging Face's free tier grants $0.10/month in Inference Provider credits per account (per HF's own pricing docs, "subject to change"), separate from and in addition to whatever per-minute/per-day rate limits the routed provider (here, Together, via HF's router) enforces. Rather than assume this is enough for Build 3's 20–30 scenario benchmark, actual per-call cost was measured by running all 7 current fixtures' real explainer prompts through the live API and reading each response's `usage.estimated_cost` field: total cost for 7 real calls was **$0.0001183** (prompt sizes 337–466 tokens, completions 178–258 tokens). Linearly projected, a full 20–30 scenario pass costs roughly **$0.00034–$0.00051** — about 0.3–0.5% of the $0.10 monthly budget, meaning the free tier comfortably supports on the order of 200 full benchmark passes per month at this model/prompt size before hitting the credit wall, not a handful. **Open risk, not fully closed:** this measurement covers only Build 1's single-explainer-call-per-scenario shape; Build 4's multi-agent core (parallel investigators, possible skeptic/verifier) and any Build 3 iteration that re-runs the benchmark repeatedly in one month could plausibly raise per-scenario call count by 3–5x, which still leaves comfortable headroom at these prices but has not itself been measured. Re-check this arithmetic once Build 3's actual scenario count and Build 4's actual per-scenario call count are known, rather than assuming this measurement still holds unchanged.

## 10. Precedence rule: sql_diff's `distinct` finding suppressed in favor of definition_diff's `aggregation` finding

**Decision:** When `sql_diff`'s `distinct` category and `definition_diff`'s `aggregation` field trace to the same underlying COUNT vs. COUNT DISTINCT fact (Case 2), the `distinct` finding is suppressed in favor of the `aggregation` finding. The DISTINCT toggle is a downstream symptom of the aggregation-definition disagreement, not an independent cause.

**Reasoning:** A read-only audit of the 6 scenario fixtures found that Case 2's `distinct` (sql_diff) and `aggregation` (definition_diff) findings both describe one SQL fact — source A uses `COUNT(DISTINCT customer_id)`, source B uses `COUNT(customer_id)` — surfaced twice by two different tools rather than representing two independent causes. Left unresolved, this double-counts the same root cause in reconciliation. This is structurally the same kind of precedence rule as Day 4's self-consistency suppression (a `SelfConsistencyIssue` suppressing the matching cross-source `DefinitionDifference`), applied to a second category pair: one finding is the authoritative account of a fact, the other is a redundant restatement of it from a different angle, and only the authoritative one should reach reconciliation.

**Implementation:** `assemble_structural_and_definitional_evidence(sql_differences, definition_differences)` in `src/self_consistency.py`, with the "same underlying fact" test in `_same_count_distinct_fact` (same file). **This decision was recorded here before any enforcing code existed** — a Day 5, Task 1 verification pass found the rule had been treated as real infrastructure across planning conversations despite having zero implementation anywhere in the codebase; Task 1b (`tests/test_structural_definitional_precedence.py`) built and proved it against a real Case 2 collision and a constructed over-fire case (a DISTINCT toggle paired with an unrelated aggregation-function change) before decision 11's Shapley-averaging engine was allowed to depend on it. Lesson for future decisions in this log: a decision entry describes an intent, not a guarantee that code exists — cross-check the implementation pointer, don't assume one.

## 11. Attribution method: pairwise averaging replaces fixed-order sequential subtraction

**Decision:** For any pair of remaining causes (after Day 4's self-consistency suppression and decision 10's distinct/aggregation suppression) that could plausibly act on overlapping rows, Day 5's reconciliation math computes both isolated counterfactual effects (each cause measured with the other held first at source A's setting, then at source B's setting) and attributes the average of the two as that cause's dollar impact — not a single fixed-order sequential subtraction. This applies uniformly to every remaining pair, without first attempting to detect whether the pair actually overlaps on real rows. Overlap-detection-before-averaging (to skip the extra counterfactual query when two causes are provably independent) is deferred to Build 3, to be revisited only if query cost at 20-30 scenarios makes it worthwhile — not built speculatively now against 6 scenarios where the extra query cost is negligible.

**Reasoning:** Real-execution testing (not static SQL reading) against synthetic row-level data for Case 2 and Case 3 confirmed genuine interaction in both — Case 2's excluded_statuses effect measured 2 under DISTINCT aggregation vs. 3 under non-distinct COUNT (driven by duplicate rows on the status boundary); Case 3's naive additive sum (850.0) missed the true reconciled value (450.0) by exactly 400, one overlap row's amount double-counted because it was excludable by two different mechanisms (date filter on one side, status filter on the other) that sequential subtraction cannot distinguish without either double-counting or dropping it. With exactly two causes per interacting pair, averaging both orderings is the exact Shapley-value solution, not an approximation, so there is no accuracy cost to always applying it. The earlier "definitional differences resolved before structural differences" fixed order (decision pending, chat-only, never committed to this log) is abandoned as empirically unsupported: every confirmed interaction found so far is definitional-vs-definitional, not definitional-vs-structural, so the original rule was never actually tested against a case where it would matter. Scope caveat, stated explicitly to avoid overclaiming: interaction has been confirmed only for definitional-vs-definitional pairs (aggregation-vs-excluded_statuses in Case 2, date_field-vs-excluded_statuses in Case 3). Definitional-vs-structural interaction (e.g., a join-type difference interacting with a definitional filter) remains untested, not ruled out — none of the 6 current fixtures happen to pair a definitional cause with a structural one on overlapping rows. This method should be re-verified, not assumed to generalize, once Build 3 authors scenarios that create that pairing. General n>2 cause interaction (requiring full Shapley averaging across more than two orderings) is also untested and deferred to Build 3 for the same reason — no current fixture has 3+ interacting causes.

## 12. Precedence rule: sql_diff's `date_field` finding suppressed in favor of definition_diff's `date_field` finding

**Decision:** When `sql_diff`'s `date_field` category and `definition_diff`'s `date_field` field trace to the same underlying date-column swap (Case 3: source A uses `order_date`, source B uses `created_at`), the `date_field` SQLStructuralDifference is suppressed in favor of the `date_field` DefinitionDifference. The mechanical structural finding is a downstream restatement of the business-meaning definitional finding, not an independent cause.

**Reasoning — precedence direction, reasoned explicitly rather than assumed symmetric with decision 10:** Decision 10 kept the business-declared `aggregation` finding (`count_distinct` vs. `count`, a human-authored config choice) over the mechanical `distinct` toggle it produces as a byproduct. The same question had to be asked here, not assumed to transfer automatically: does the `date_field` DefinitionDifference carry the same kind of independent, human-authored information the `aggregation` finding did in decision 10, or is it just a second mechanical restatement with extra steps? Checked directly: when both sides declare their `date_field` (the fully-symmetric case with decision 10 — both `source="declared"`, `confidence="high"`), the definitional finding states an intentional analyst choice ("this dashboard reports by order date, that one by record-creation date") — exactly the kind of business-meaning explanation decision 10 judged more valuable to a human reader than a bare structural fact. Case 3 itself is the asymmetric case — B has no declared definition, so its `date_field` value is inferred straight from the same SQL `sql_diff` already parsed, and the field's overall `source`/`confidence` is capped to `"inferred"`/`"medium"` by `diff_definitions`'s weakest-link rule (`src/definition_diff.py`). The suppression rule is nonetheless applied uniformly regardless of confidence, matching decision 10's own rule (which also does not gate on confidence) and keeping one consistent rule per category pair rather than two. Caveat, stated explicitly rather than left implicit: this has been proven only at `confidence="medium"` (Case 3, and the constructed over-fire case below); a `confidence="low"` inferred `date_field` (ambiguous SQL, multiple or zero date-like columns) suppressing an always-mechanically-correct structural finding is untested and could plausibly warrant the opposite call, since the structural finding cannot be wrong about what the SQL literally does, while a low-confidence guess can. Flagged for the Build 3 audit below, not resolved here.

**Reasoning — dollar-value handling, checked against the Case 7 lesson rather than assumed safe:** Day 7 Part A (this same build day) found that suppressing a finding can silently discard a real, separate dollar contribution if the suppressed finding represented an independent, additional correction step (Case 7: self-consistency correction, then a further, separate cross-source correction — two sequential deltas that had to be summed). This collision was checked against that exact risk and found NOT to have it: unlike Case 7's two sequential corrections, `sql_diff`'s `date_field` finding and `definition_diff`'s `date_field` finding, when they trace to the same fact, describe the *same single* SQL mutation (swap the date column) — not two chained ones. `construct_corrected_query` applied once, using the surviving `DefinitionDifference`, already performs the complete correction; there is no second, independent dollar-bearing step to fold in. Verified directly: Case 3's `ReconciliationLineItem` for `date_field`, computed the normal way after suppression, reproduces exactly the same dollar figure (-400.0, negated from Day 5 Task 2's committed +400.0) that was already proven correct before this decision existed — nothing is missing.

**Pattern note — third occurrence of the same class of gap:** This is the third time this project has discovered two independent tools producing findings that trace to one underlying fact, with no suppression rule reconciling them, only after building further downstream logic that depended on the evidence being non-redundant: Day 4's self-consistency-vs-cross-source collision (a `SelfConsistencyIssue` and a `DefinitionDifference` both describing one source's own field), decision 10's `distinct`-vs-`aggregation` collision, and now this `date_field`-vs-`date_field` collision, all found by different downstream work (Day 4 Part 2's own precedence rule, a Case 2 audit before decision 10's engine was trusted, and Day 7 Task 1's `ReconciliationLineItem` assembly, respectively) rather than by deliberately searching for them. **Forward note:** a systematic audit of every `SQLStructuralDifference` category against every `DefinitionDifference` field for this same risk should happen before Build 3's larger scenario set is authored, rather than continuing to discover these one fixture at a time — the categories not yet audited this way are `filter`, `distinct` (audited, decision 10), `join_type`, `aggregation` (audited, decision 10), `date_field` (audited, this decision), `grouping`, and `other`.

**Implementation:** `_same_date_field_fact` and the extended `assemble_structural_and_definitional_evidence`, both in `src/self_consistency.py` — the same function decision 10 lives in, extended rather than duplicated, since both are "an sql_diff structural finding collides with a definition_diff definitional finding" instances of one general shape. "Same underlying fact" is defined precisely, mirroring `_same_count_distinct_fact`'s precision standard: not mere category co-presence, but a side-matched exact equality between the structural finding's own referenced columns (parsed from its snippet text via sqlglot, requiring exactly one unambiguous column per side) and the definitional finding's own declared/inferred values. Proven against the real Case 3 collision (`test_case_3_date_field_suppressed_excluded_statuses_survives`) and a constructed over-fire case where a structural finding references two ambiguous date columns on one side while the definitional finding differs on a completely unrelated column pair (`test_does_not_over_fire_on_unrelated_date_field_findings`), both in `tests/test_structural_definitional_precedence.py` — built and proven before being relied upon, unlike decision 10's own history.

## 13. `known_gap` and seed-execution dollar figures were not scale-calibrated for Cases 1–5 — discovered, then resolved

**Decision (original, Day 7 Task 2):** Not a fix at the time — recorded as a known, named gap rather than silently smoothed over, per this project's own standing rule for a fixture that fails a check without a code bug behind it. `assemble_investigation_evidence`'s `unexplained_residual` (Build 1, Day 7, Task 2) was large for Cases 1–4 (91–99.9% of `known_gap` unexplained) even though every cause found in those scenarios was correctly identified and correctly signed (same direction as `known_gap` in every case, verified explicitly). Not treated as a defect to fix in that task.

**Resolution (Build 1, Day 7, Task 3):** Fixed. `reported_value_a`, `reported_value_b`, and `known_gap` for Cases 1–4 (`tests/fixtures/scenarios.py`) were replaced with values derived from executing each scenario's actual as-written SQL against its actual seed data (`{seed_table}_a.duckdb`/`{seed_table}_b.duckdb`), matching Case 7's original standard exactly. Case 5 and Case 6 were checked the same way and found to already be correctly calibrated — their executed values matched their existing hand-typed figures exactly, so no numbers changed there, but the check was performed, not skipped. Case 7 was left untouched (already calibrated since the Day 4 close-out). No SQL, declared definitions, or seed data were altered — only the three top-level `Scenario` fields. This is now the uniform convention for all 7 fixtures, and applies to any fixture added later: a scenario's `reported_value_a`/`reported_value_b`/`known_gap` must be derived from real execution of its own SQL against its own seed data, never hand-typed independently of it.

**Result:** Every one of Cases 1–4 now reconciles to an exact 0.0 residual (0.0% of `known_gap`), not merely "near zero" — the single or paired cause found in each case fully and exactly accounts for the recalibrated gap. This confirms the reconciliation math itself (Shapley pairing, self-consistency folding, decision 10/12 suppression, sign convention) was correct all along; only the fixture calibration was off. Case 5's residual remains 100% of `known_gap` (3800.0), unchanged and correct by design — no cause exists for it to find. Case 6 remains 0/0, unchanged. Full before/after figures and the recalibrated 7-fixture table are recorded in the Day 7 Task 3 session report, not duplicated here.

**Reasoning (why the gap existed):** `Scenario.known_gap`'s own docstring (`src/scenario.py`, written back in Build 1 Day 1 Part 2) already stated the two numbers were never *required* to match in magnitude: "known_gap is the hand-authored, independently-asserted expected value — it is not derived from executing against seed_table." Cases 1–4's `reported_value_a`/`reported_value_b` had been authored at a realistic dashboard scale (hundreds of thousands), while their seed data was built at a much smaller, independently-chosen scale for tractable hand-verification (tens to low thousands) — the two were never calibrated to reconcile against each other, even though nothing in the schema forbade doing so. Case 7 was the sole exception at the time, and the only non-trivial case with a near-zero residual before this resolution: its `reported_value_a`/`reported_value_b` were deliberately set equal to real seed-execution figures (300.0/100.0) when the fixture was built during the Day 4 close-out, specifically so the precedence rule could be proven against a real, checkable number. Cases 1–5 had never been given that same treatment — Task 3 gave it to them.

This was a genuinely new finding when Task 2 surfaced it, not a rediscovery of an already-flagged item: every prior verification in this project (Day 5's Shapley proofs, Day 6's self-consistency dollar figures, Day 7 Task 1's line-item assembly) compared execution results against *other* execution results (hand-verified SQL variants) or checked *direction* against `known_gap`, never magnitude-reconciled against it directly. Task 2 was the first point in the project where that direct comparison happened, which is why the gap surfaced only then — and why Task 3 could fix it immediately once named, rather than requiring further investigation.

**Consequence, stated plainly (post-resolution):** the sum-equals-`known_gap` check (`total_dollar_impact + unexplained_residual == known_gap`) holds exactly for all 7 fixtures, and remains an algebraic identity of how `unexplained_residual` is *defined* (the same caveat decision 11's Shapley sum-check already carries) regardless of calibration — it alone never proved the residual was small. What changed is the separate, meaningful claim: whether the residual is actually small now holds for Cases 1, 2, 3, 4, and 7 (all exactly 0.0%), in addition to Case 5 (100%, correctly, by design — no cause exists to find). No fixture is left in the "large residual with no explanation" state this decision originally described.

**Forward note (superseded by the resolution above, kept for history):** the original entry recommended calibrating future fixtures the way Case 7 was, without retroactively touching Cases 1–5 due to the cost of rescaling already-verified numbers. Task 3 concluded that cost was worth paying — every downstream committed test that depended on the old figures was re-run and updated deliberately (not force-fit), confirming the reconciliation logic itself needed no changes. The recommendation that stands going forward: any fixture added in Build 3 or later must have `reported_value_a`/`reported_value_b`/`known_gap` derived from real execution against its own seed data from the moment it's authored, per the Resolution paragraph above — not deferred and revisited later the way Cases 1–6 were.

## 14. LLM explainer grounding defects, observed and characterized for Build 3's unsupported-claim-rate checker (not fixed — deliberately left as test targets)

**Decision:** Two real, observed defects in the Hugging Face explainer's prose (Build 1, Week 2 Day 1, PR #39's live 7-fixture verification) are recorded here with enough reproduction detail that whoever builds Build 3's unsupported-claim-rate checker can write a targeted test for each pattern, rather than relying on a vague "check for hallucination" mandate. Per this project's own standing rule (see decision 10's lesson), a finding recorded without enough specificity to act on is close to not being recorded at all.

**Defect 1 — sign-dropping on a correctly-sourced dollar figure (Case 2, `case_02_multi_cause`):** `InvestigationEvidence.reconciliation` for this fixture contains a line item with `cause="aggregation: source_a declares 'count_distinct', source_b declares 'count'"` and `dollar_impact=-1.5` exactly (confirmed via `assemble_investigation_evidence(CASE_2_MULTI_CAUSE)`, not assumed). The prompt built by `_format_evidence_prompt` (`src/explainer.py`) renders this correctly-signed, as `dollar_impact=-1.50` (the `:+.2f` format spec). The live model response narrated it as: *"the difference in aggregation methods, with source A using 'count_distinct' and source B using 'count', has a dollar impact of $1.50"* — the magnitude is exactly right, the sign is silently dropped. This is not a fabricated cause or a fabricated number; it is a real number stripped of a real, given sign. **Test pattern for Build 3:** for every `ReconciliationLineItem` with a negative `dollar_impact`, check whether the explainer's prose states that figure's magnitude without an accompanying negative/"reduces"/"offsets"/"negative impact of"-type qualifier — a magnitude-only mention of a negative figure is the specific shape of this defect, distinct from a magnitude mismatch (wrong number entirely) or a fabricated cause (a number/cause absent from evidence).

**Defect 2 — narrating an empty category as a "cause that does not exist" (Case 4, `case_04_governance_drift`):** This fixture's `definition_differences` and `sql_differences` are both empty lists (self-consistency-only scenario, by design — the precedence rule suppresses the one real cross-source finding into `self_consistency_issues` instead). `_format_evidence_prompt` renders each empty category as a plain `"- None."` line, exactly as it does for every other fixture with an empty category (Cases 1, 3, 5, 6, 7 all have at least one empty category rendered the same way, all without triggering this). The live model response for Case 4 specifically narrated these as invented, then-negated causes: *"We have also identified a reconciled cause that is a result of definitional differences between source A and source B. However, this cause does not exist, and the dollar impact is zero... Another reconciled cause is related to SQL structural differences between the two sources. However, this cause also does not exist, and the dollar impact is zero."* No false cause or number reaches a final claim (each is explicitly negated in the same sentence), but the narrative structure invents a "candidate cause" only to retract it — confusing, and a warning sign for how this class of model handles an all-empty section next to a populated one. **Test pattern for Build 3:** for a fixture where at least one evidence category is empty and at least one is populated, check whether the prose introduces language implying a cause exists in the empty category (e.g. "a[nother] reconciled cause... however, it does not exist" or equivalent hedge-then-retract phrasing) rather than simply omitting or plainly stating "none" for that category — the retraction saves it from being a false claim, but the pattern itself (inventing a candidate to negate) is what to flag, not just bare factual accuracy of the final sentence.

**What was deliberately NOT done:** neither defect was prompt-engineered away. Per this task's own instruction, a defect observed on Cases 5/6 (the two fabrication-risk cases) would have been reportable as a finding about the model's behavior rather than silently patched — the same standard applies here: these are real, current behaviors of `meta-llama/Llama-3.1-8B-Instruct` against this project's current prompt (`_format_evidence_prompt`), not resolved by this decision, and a future prompt-wording change or model swap should be re-verified against both patterns rather than assumed to have fixed them.

**Scope note:** both defects were observed on a single live run per fixture; LLM output is non-deterministic, so a re-run may phrase things differently even against the same evidence and prompt. What is being recorded is the *category* of defect (sign-dropping on real figures; hedge-then-retract narration of empty categories), confirmed present at least once each, not a claim that either reproduces identically on every call.

## 15. `Scenario.seed_table`'s meaning overloaded for freshness scenarios, rather than introducing two clean new fields

**Decision:** Build 2, Day 1 needed to represent a freshness-testing scenario's two required snapshots per side (a "stale/as-delivered" version and a "complete" counterfactual). Rather than add two new fields and leave `seed_table` untouched, `seed_table`'s existing meaning was reinterpreted for freshness scenarios specifically: it now names the "stale/as-delivered" snapshot when a freshness cause is being tested, while a new field, `freshness_complete_seed_table: str | None = None`, names the second, "complete" counterfactual pair. For every non-freshness scenario (all 7 Build 1 fixtures), `seed_table` means exactly what it always meant — this is a conditional second meaning layered onto one field for a subset of scenarios, not a renaming.

**Reasoning:** This session's own brief suggested a single base name with a four-way suffix chain instead (`{seed_table}_a_complete.duckdb`/`{seed_table}_a_stale.duckdb`/`..._b_complete...`/`..._b_stale...`), which would have kept `seed_table` a single unambiguous concept and made the stale/complete distinction a pure suffix rather than a field-level reinterpretation. The reinterpretation approach was chosen instead for two reasons: (1) it requires zero changes to any already-committed code that resolves `seed_table` (`scripts/build_seed_data.py`, `reconciliation_assembly.py`, `self_consistency.py` all keep resolving it exactly as they do today, freshness fixture or not); (2) it avoids a physical duplicate "_stale" file that would just be a second copy of data `seed_table`'s own per-side files already provide — the "stale" snapshot for a freshness fixture is not new data, it's the same data every other fixture's `seed_table` already names.

**The tradeoff, stated plainly:** `seed_table` is now a field whose meaning depends on whether `freshness_complete_seed_table` is set on the same `Scenario` — a reader (or a future Code session) who trusts `seed_table`'s surface meaning ("the scenario's backing data") without checking the sibling field can be wrong about what it represents for a freshness fixture specifically. This is the same shape of risk decision 13 named directly: an undocumented dual-meaning field is exactly what caused the `known_gap`/seed-execution calibration confusion there. The mitigation taken here, to avoid repeating that mistake: `seed_table`'s own docstring (`src/scenario.py`) was updated in the same commit, not left as-is — it now states explicitly that for a freshness scenario, `seed_table` specifically names the stale/as-delivered snapshot, and points to `freshness_complete_seed_table` for the complete counterfactual. The dual meaning is documented at the point of overload, not left implicit.

**Recorded here, not just in the docstring, because of decision 10's own lesson reversed:** decision 10 warned that "a decision entry describes an intent, not a guarantee that code exists." The reverse failure is just as real -- a design choice documented only in a docstring, with no entry in this log, is invisible to a future audit or a reviewer of the public repo who checks `docs/decisions.md` for architectural judgment calls without reading every module's docstrings first. This entry exists so that check finds something.

**Consequence for Build 2, Day 2+:** whoever writes the freshness-detection logic, the seed-data build script, and the first freshness fixture must resolve `seed_table` as the stale snapshot and `freshness_complete_seed_table` as the complete one -- not assume `seed_table` alone is sufficient, and not assume the two fields are independent of each other's meaning. If a future session finds this overload confusing in practice (e.g. it becomes hard to tell, reading a fixture alone, whether `seed_table` is being used in its freshness sense or its plain sense), splitting into two always-populated fields remains available as a follow-up refactor -- not done now, since no fixture yet exists to prove the confusion is real rather than hypothetical.

## 16. `late_arriving_data` deferred to Build 3, not built in Build 2

**Decision:** `late_arriving_data` (the fourth `DataQualityIssue` category, `src/schema.py`) is deferred to Build 3. It will not be built in Build 2, Day 5 or any remaining Build 2 session. Build 2 ships with exactly three working checks -- `check_stale_extract`, `check_missing_partition` (Day 3, `_check_completeness`), and `check_referential_integrity` (Day 4, `_orphan_count`) -- not four. This is a scope decision made deliberately, not a timeline slip: the category isn't late, it's moved.

**Reasoning:** `late_arriving_data` was assumed, when the `DataQualityIssue.category` Literal was written (Build 2, Day 1), to be buildable the same mechanical way `missing_partition` extended `stale_extract` in Day 3 -- reuse an existing detection primitive under a new category label, distinguished only by fixture construction. That assumption was tested directly in this session's own planning discussion, with a precise question: is `late_arriving_data` honestly distinct from `stale_extract`, or would it just be a third row-count check wearing a third label? The test posed was: does re-running the SAME query, with the SAME extraction/query logic, at a LATER point in time, against data that has since fully arrived, produce the complete result -- i.e. is this genuinely about *when* rows arrived, not *whether* a different snapshot or a differently-scoped query is needed to see them? If yes, that is real lateness, and detecting it needs a mechanism `_check_completeness`/`_orphan_count` do not have: a per-row EVENT-TIME column (when the row's underlying business event happened) versus an INGESTION-TIME column (when the row actually landed in the table), plus a calibrated cutoff distinguishing "arrived late but did arrive" from "still missing." If no -- if the only way to see the complete data is a different snapshot file or a structurally different query -- then whatever that fixture is testing is `stale_extract` (or `missing_partition`) under a mislabeled name, not a new category at all.

**This test was posed and never passed.** No fixture, real or hypothetical, was constructed this session that cleanly demonstrates the "yes" branch using only this project's existing seed-data conventions (a fixed DuckDB file per side, built once by `scripts/build_seed_data.py`, with no notion of "current wall-clock time" or "a query re-run later"). Every attempt to sketch one either collapsed into a second `stale_extract`-shaped snapshot pair (the "no" branch) or required inventing simulated time-passage machinery (an explicit "as-of" parameter threaded through the seed-data build and the check function) that is a genuinely new mechanism, not a documentation exercise -- exactly the kind of scope growth this project's own "minimum code that solves the problem" convention exists to catch before it's built speculatively.

**What a future Build 3 session must resolve before building this category:**
1. A schema decision: does `late_arriving_data` need new fixture-level fields (an event-time column distinct from the ingestion/extraction time already implicit in `seed_table`, and something representing "the query's as-of time") added to the seed-data shape, or can it reuse `Scenario.freshness_complete_seed_table`'s existing stale/complete pairing by treating "late" rows as present in `complete` and absent from a *third*, genuinely time-gated snapshot? This has not been decided -- both are plausible, neither has been tried.
2. A worked fixture that actually passes the test above: construct it FIRST, prove it is not secretly `stale_extract`/`missing_partition` in disguise, before writing `check_late_arriving_data` -- mirroring how Day 4 confirmed a real fact/dimension relationship existed before writing `check_referential_integrity`, not the reverse order.
3. Re-audit `_CONFIDENCE`'s fixed `"high"` constant (`src/data_quality.py`) against this category specifically -- its own comment already flags that `late_arriving_data`/`referential_integrity` "may have a genuine reason to vary confidence" unlike the row-count checks' mechanical certainty; `referential_integrity` turned out not to need this (an orphan-row count is just as mechanically exact as a row-count diff), but `late_arriving_data`'s cutoff-based judgment call plausibly does, and this has not been re-examined since that comment was written speculatively in Day 2.

**Pattern note -- this is the third item riding into Build 3 under the same shape ("discovered mid-build, needed a design pass Build 2 couldn't absorb"), not three unrelated slips:** decision 12's own forward note (a systematic audit of every `SQLStructuralDifference` category against every `DefinitionDifference` field for cross-tool collisions) and decision 11's own scope caveat (n>2 cause interaction, and definitional-vs-structural pair interaction, both untested by the current fixture set) were each deferred the same way -- a real gap, named explicitly rather than silently assumed safe, carried forward with a stated reason rather than quietly dropped. `late_arriving_data`'s deferral joins that same list. A future session auditing "what did Build 2 actually ship versus what the Build Skeleton originally scoped" should expect exactly these three gaps, not be surprised by any of them.

## 17. `ReconciliationLineItem` and `DataQualityIssue` dollar figures can restate the same fact -- a legibility risk, not a code defect

**Decision:** `DataQualityIssue.dollar_impact` figures are never summed against, or cross-referenced with, `ReconciliationLineItem.dollar_impact` figures anywhere in this codebase -- `data_quality_issues` remains additive-evidence-only (Build 2, Day 5's locked decision). This decision does not change that arithmetic boundary; it records a risk that boundary does not, by itself, fully close: the two lists can describe the *same* underlying dollar delta via two independent computation paths, with nothing in the schema or the assembled `InvestigationEvidence` object stating that to a reader.

**Reasoning, grounded in a real proof, not a hypothetical:** Build 3, Day 1, Part 2 built `CASE_12_JOIN_ORPHAN_COLLISION` specifically to test overlap #7 (`sql_diff`'s `join_type` category vs. `check_referential_integrity`) and Part 4 ran it through `assemble_investigation_evidence` directly. The result, confirmed by execution: `reconciliation` contains one `ReconciliationLineItem` for the `join_type` correction, `dollar_impact=300.0`; `data_quality_issues` separately contains one `DataQualityIssue` for the referential-integrity orphan, `dollar_impact=300.0`. Both figures are numerically identical because both are measuring the exact same correction (excluding the one orphan row) via two independent code paths (`single_cause_attribution` applied to a join-type correction vs. the same function applied to an FK-filter correction) that happen to converge on the same delta. Summing them ($300 + $300 = $600) would double Case 12's real `known_gap` of $300. **`assemble_investigation_evidence`'s own math is unaffected by this** -- `unexplained_residual` for Case 12 is exactly `0.0`, computed entirely from `reconciliation`'s single line item, with `data_quality_issues` never entering that arithmetic at all (proven directly, not assumed, in Part 4). The risk is entirely on the READING side: a human, a report, or a future explainer prompt that treats `reconciliation` and `data_quality_issues` as two independent lists of causes to add together would be wrong, and nothing today would stop that mistake.

**Mitigation, scoped deliberately narrow:** a one-sentence caveat added to `InvestigationEvidence`'s own docstring (`src/schema.py`) stating that a `data_quality_issues` entry's dollar figure may restate a cause already counted in `reconciliation`, and must never be summed against it by a future reader, report, or explainer prompt. This is the ONLY code change this decision makes. A machine-readable pairing mechanism (e.g. a `related_finding_note` field cross-linking the two lists) was explicitly considered and rejected as speculative infrastructure for a risk that is currently a reading hazard, not a proven need with a concrete consumer -- if a future build genuinely needs to detect this programmatically (e.g. to drive a real suppression rule the way decisions 10/12 did for `sql_diff`/`definition_diff` collisions), that is new, separately-scoped work, not something this docstring caveat should grow into on its own.

**Forward note, load-bearing for whoever builds it:** `src/explainer.py` still does not render `data_quality_issues` in its prompt (Build 2, Day 1's original deferral, still standing as of this entry). This caveat is inert today because of that deferral alone -- the moment `data_quality_issues` rendering is added, this decision's mitigation becomes load-bearing, and whoever does that work must read this entry first, not discover the double-narration risk fresh the way Part 2/4 did for Case 12.

## 18. Filter/excluded_statuses suppression rule -- confidence-gated, reverse precedence direction from decisions 10/12

**Decision:** When `sql_diff`'s `filter` category and `definition_diff`'s `excluded_statuses` field trace to the same status column, AND the `excluded_statuses` `DefinitionDifference`'s confidence is EXACTLY `"low"`, the `excluded_statuses` finding is suppressed and the `filter` finding survives. Scoped deliberately narrow to `confidence="low"` only -- a `"medium"`/`"high"`-confidence `excluded_statuses` finding colliding with a `filter` finding is explicitly NOT handled by this rule.

**Reasoning:** This is the third occurrence of the "two tools trace to the same fact" pattern (after decision 10's `distinct`/`aggregation` collision and decision 12's `date_field`/`date_field` collision), but resolved in the OPPOSITE direction on purpose, not by oversight. Decisions 10 and 12 both kept the business-declared/inferred DEFINITIONAL finding over the mechanical structural one, reasoning that a human-authored config choice (or its inferred equivalent) carries more meaning than a bare structural fact -- and that precedent held regardless of the definitional finding's confidence level. This rule inverts that: `filter`'s presence/absence is mechanically certain (a `COUNT(*)`-grade fact, the same certainty class `SQLStructuralDifference` findings already carry), while a `confidence="low"` `excluded_statuses` value is, by `_infer_excluded_statuses`'s own documented contract, a guess made when zero or multiple status predicates were found -- it carries no more certainty than the mechanical fact it collides with, so there is nothing lost by keeping only the mechanical one. This is decision 12's own previously-unresolved caveat -- "a `confidence="low"` inferred `date_field` suppressing an always-mechanically-correct structural finding is untested and could plausibly warrant the opposite call" -- now actually tested, for the analogous `excluded_statuses` case, and found to warrant exactly that opposite call.

**Proven, not asserted:** built and tested against the real Case 13 collision (Build 3, Day 1, Part 2/6) and two required over-fire cases, the same standard decisions 10/12 were each held to before being trusted: a `confidence="medium"`/`"high"` `excluded_statuses` finding colliding with a filter finding does NOT suppress (proving the confidence gate actually gates); a filter finding on an unrelated (non-status) column paired with a genuine low-confidence `excluded_statuses` finding does NOT suppress (proving the "same fact" check is a real column-identity check, not mere category co-presence).

**Explicit scope boundary, named as an open item, not solved by extrapolation:** what happens when a `confidence="medium"`/`"high"` `excluded_statuses` finding collides with a `filter` finding on the same column is undecided. It is tempting to assume the same reversed-direction logic should simply not apply there (since a medium/high-confidence value is presumably "real," the definitional finding should presumably win the way decisions 10/12's own findings did) -- but that has not been tested, and this decision deliberately does not extend to cover it. `assemble_structural_and_definitional_evidence`'s implementation matches this exactly: both findings survive untouched whenever `excluded_statuses`' confidence is anything other than `"low"`, per its own over-fire test.

**Implementation:** `_same_filter_exclusion_fact` and the extended `assemble_structural_and_definitional_evidence`, both in `src/self_consistency.py` -- the same function decisions 10/12 already live in, extended a third time rather than duplicated, matching the file's own established pattern. Unlike `_same_date_field_fact`, there is no stored "which column" value to compare on the definitional side (`_infer_excluded_statuses` is hardcoded to the bare column `"status"`, with no per-instance column identity on a `DefinitionDifference`) -- the column check is necessarily one-sided, reading whichever of the `filter` finding's own two snippets actually parses (`_diff_filters` is presence-only, so exactly one side has a real predicate).

## 19. Ambiguous-scenario 3+-cause routing: benchmark-layer wrapper (A3-ii), not a relaxed guard

**Decision:** For ambiguous scenarios (`BenchmarkEntry.is_ambiguous=True`) that hit `assemble_investigation_evidence`'s 3+-remaining-causes guard, the guard is not relaxed and `assemble_investigation_evidence` itself is not modified -- it keeps raising exactly as before, for every scenario, ambiguous or not. Instead, a new benchmark-layer wrapper, `assemble_investigation_evidence_for_benchmark` (`tests/fixtures/benchmark_pipeline.py`), calls `assemble_investigation_evidence` normally and catches the specific 3+-causes exception only when `entry.is_ambiguous` is `True`. On catching it, the wrapper returns a `PartialInvestigationEvidence` -- a structurally independent type, not a subclass of `InvestigationEvidence` -- containing every individual finding (`definition_differences`, `sql_differences`, `self_consistency_issues`, `data_quality_issues`) already computable before the guard would have fired, with `reconciliation=[]` and `unexplained_residual=None` rather than a fabricated number. For `entry.is_ambiguous=False`, the same exception re-raises completely unchanged -- this wrapper never widens tolerance for a genuine technical-scenario failure.

**Reasoning (historical -- the triggering case this describes no longer reaches this code path; see the Current status paragraph below):** This tied directly to why it was needed at the time, not to a hypothetical. `AMBIGUOUS_REVENUE_RECOGNITION` (Build 3, Day 2, Part 3, issue #79) -- the first ambiguous scenario this project authored -- hit a real, previously-untested case while being built from a natural, plausible business narrative, not a synthetic stress test: both sides declare real, `confidence="high"` metric definitions (`date_field`, `excluded_statuses`), and the deferred-revenue side's status exclusion also produces a real `sql_diff` `filter` finding on the same column. Decision 18 explicitly left the `confidence="medium"`/`"high"` `filter`/`excluded_statuses` collision unsuppressed -- both findings survived, on purpose, since that direction was never tested (decision 18's own named open item). With no suppression to reduce the count, this scenario reached 3 remaining cross-source causes and `assemble_investigation_evidence` correctly refused to guess, per decision 11's own untested-n>2 scope. Two other options were considered and rejected before choosing this one:
- **A2 (relaxing the guard universally), rejected:** loosening the 3+-causes guard for every scenario, not just ambiguous ones, would reopen decision 11's untested n>2 interaction scope for *technical* scenarios too -- a much broader change than the actual problem required, and one that would let a real technical-scenario failure (a genuine, currently-uncaught 3+-cause interaction bug) through silently, exactly the kind of gap-patching this project has repeatedly caught itself doing and stopped doing.
- **A3-i (ambiguity-awareness inside `Scenario`/`assemble_investigation_evidence` directly), rejected:** threading `is_ambiguous` into `Scenario` or `assemble_investigation_evidence` itself would reverse the deliberate `Scenario`/`BenchmarkEntry` separation established the prior session (`BenchmarkEntry` wraps `Scenario` rather than modifying it, specifically so benchmark-only metadata never leaks into the evidence-representation schema) for no necessary gain -- the same problem is fully solvable at the benchmark layer alone.

A3-ii (this decision) was chosen because it solved the actual problem as it existed then -- a genuinely ambiguous scenario's individually-found causes need to reach a benchmark scorer even when full reconciliation can't be computed -- without touching any already-proven, already-tested code path in `src/reconciliation_assembly.py` or `src/self_consistency.py`. The architecture and reasoning above remain valid design -- what changed is only that decision 22 later closed the specific gap this wrapper existed to route around.

**Current status, Build 3 Day 3 Part 1 (added for honesty, not to relitigate the decision):** `AMBIGUOUS_REVENUE_RECOGNITION`, plus `AMBIGUOUS_CUSTOMER_COUNTING` and `AMBIGUOUS_ATTRIBUTION` (both authored later under the same shape, Build 3 Day 2 Part 7), were this wrapper's only real, committed proof cases. Decision 22 (below) extended `_same_filter_exclusion_fact`'s suppression to fire at `confidence="medium"`/`"high"` too, which reduces exactly this collision shape from 3 remaining causes to 2 -- so as of decision 22, all three scenarios complete DIRECTLY through `assemble_investigation_evidence`, and none of them reaches this wrapper's catch clause any more. **Confirmed directly, Build 3 Day 3 Part 1: running all 6 currently-committed ambiguous `BenchmarkEntry` scenarios through `assemble_investigation_evidence_for_benchmark` returns a real `InvestigationEvidence` for every one of them -- zero currently return a `PartialInvestigationEvidence`.** `tests/test_benchmark_pipeline.py` imports `PartialInvestigationEvidence` only to assert results are *not* instances of it; the one test that exercises the wrapper's actual exception-catching code (`test_technical_scenario_3plus_causes_still_raises_through_wrapper`) uses `is_ambiguous=False`, which takes the re-raise branch, not the catch-and-return branch -- so, as of that entry, no committed test of any kind exercised the wrapper's `is_ambiguous=True` catch-and-return path, not just no committed scenario.

**Resolved, Build 3 Day 3 Part 3: the wrapper is being KEPT, deliberately, in a dormant state -- not retired.** This closes the keep-vs-retire question the paragraph above left open; it is not a question for a future session to revisit absent new information. Retiring the wrapper would discard real, proven design work -- the A2/A3-i rejected-alternatives analysis above and the `PartialInvestigationEvidence` type-boundary discipline (a structurally independent type, not a subclass of `InvestigationEvidence`, specifically so a benchmark-only escalation outcome can never quietly widen what "a complete evidence bundle" means in production schema) -- for a problem shape that remains plausible to recur, not merely a hypothetical one invented to justify keeping unused code. The wrapper exists to handle 3+ high-confidence causes surviving suppression after `assemble_investigation_evidence`'s guard fires; decision 22 closed the one collision shape (`filter`/`excluded_statuses` at any confidence) that was producing this in this project's current 6 ambiguous scenarios, but decision 23's own stated boundary -- reaching more ambiguous scenarios "would require either a 4th `DeclaredDefinition` field... or accepting a forced, artificial narrative," with a schema extension explicitly named as real, separately-scoped future work, not ruled out -- means a 4th `DeclaredDefinition` field is a live possibility, not a closed door. Any such extension would introduce new collision shapes between fields that no current suppression rule (decisions 10, 12, 18, 22) was ever written with a 4th field in mind to cover. The wrapper is the one piece of this project's architecture already built and tested for exactly that failure mode, regardless of which specific fields eventually produce it.

The cost of keeping it dormant is close to zero: it is isolated entirely to the benchmark test-fixtures layer (`tests/fixtures/benchmark_pipeline.py`), touches no production code path (`src/reconciliation_assembly.py`, `src/self_consistency.py`, `src/explainer.py` all remain unaware of its existence), and its one dedicated test (`test_technical_scenario_3plus_causes_still_raises_through_wrapper`) already proves its re-raise branch against a synthetic construction that does not depend on any currently-committed scenario reaching 3+ causes. Carrying a small amount of currently-dormant, already-tested code is a materially cheaper position than deleting a working escalation mechanism and having to redesign it from scratch if a future schema extension reintroduces the exact shape it was built to handle.

This does not claim the wrapper will necessarily be needed again, or that a 4th `DeclaredDefinition` field is planned or scheduled -- decision 23 left that explicitly out of scope for Build 3, and this entry does not change that. It claims only that, given the wrapper is fully built, tested, and isolated from production code, retiring it now would trade a real, if currently unexercised, capability for no corresponding benefit.

**Sub-note on the schema question, stated explicitly rather than left as a footnote:** the first implementation attempt (Build 3, Day 2, Part 4) widened `InvestigationEvidence.unexplained_residual` directly to `float | None` in `src/schema.py`, to carry the wrapper's escalated-path output. This was reverted in the same session (Part 5), on review: `InvestigationEvidence` is production schema, consumed by `src/explainer.py` and every other assembly caller -- loosening a shared production field to accommodate one benchmark-only edge case would have let a benchmark-only outcome quietly widen what "a complete evidence bundle" is allowed to mean everywhere else in the codebase. `PartialInvestigationEvidence` exists specifically to keep that boundary intact: `src/schema.py`'s `InvestigationEvidence.unexplained_residual` is confirmed byte-identical to its pre-Part-4 definition (`git diff` against the commit before PR #82, empty), and the escalated path's honest partial-result type lives entirely in `tests/fixtures/benchmark_pipeline.py` instead.

**Scope boundary, stated plainly:** this decision resolves the `confidence="medium"`/`"high"` `filter`/`excluded_statuses` collision for **ambiguous scenarios only**, by routing to escalation rather than by suppression. It does **not** resolve decision 18's own named gap for **technical (non-ambiguous)** scenarios -- what should happen when a `confidence="medium"`/`"high"` `excluded_statuses` finding collides with a `filter` finding on a *technical* scenario remains genuinely open, exactly as decision 18 left it. This decision should not be read as having quietly closed that gap; it only gives ambiguous scenarios a different, correct way to reach the same 3+-cause situation without needing that gap resolved first. **Superseded, Build 3 Day 2 Part 15, decision 22:** that gap IS resolved there, for technical and ambiguous scenarios alike -- decision 22 extends the underlying suppression rule itself (`_same_filter_exclusion_fact`), unconditional on `is_ambiguous`, rather than adding a second benchmark-layer workaround.

## 20. `apply_filter_correction`: ADD direction only, and a disproven hypothesis about the three wrapper-routed scenarios

**Decision:** `sql_diff`'s `filter` category gains a corrected-query mutation rule (`apply_filter_correction`, `src/query_mutation.py`, wired into `construct_corrected_query`'s dispatch), but for the ADD direction only: correcting a side that is MISSING a filter predicate, toward the other side's real predicate (sourced directly from the `SQLStructuralDifference`'s own `query_a_snippet`/`query_b_snippet` -- no signature change to `_single_cause_line_item`/`_shapley_pair_line_items` was needed, since the difference object already carries what's needed, the same mechanism `join_type`'s own default-target extraction already uses). The REMOVE direction -- a side WITH an extraneous predicate the other side lacks, e.g. `CASE_13_FILTER_EXCLUDED_STATUSES_COLLISION`'s exact shape -- is explicitly out of scope and raises a distinct, clear error rather than being guessed at.

**Reasoning:** This closes the specific gap named in decision 18's own forward note and CONTEXT.md's own long-standing Open Items entry: `filter` was the one `SQLStructuralDifference` category flagged repeatedly (Build 3 Day 1 Parts 4/5/6, the Build 3 Day 2 Part 12/13 sweep) as having no correction mechanism at all, blocking overlap #4's full-pipeline processing for technical scenarios and any `filter`-shaped ambiguous scenario alike.

**A real, tested hypothesis, disproven by direct execution -- worth recording precisely because it turned out false:** before this fix, it was plausible that `AMBIGUOUS_REVENUE_RECOGNITION`/`AMBIGUOUS_CUSTOMER_COUNTING`/`AMBIGUOUS_ATTRIBUTION` (Build 3 Day 2 Parts 3/7) reached the 3+-causes guard partly *because* `filter` was uncorrectable -- i.e. that fixing `filter` might reduce one of them from "3+ causes, escalate via wrapper" down to a completable 2-cause pair. Re-running all three directly after this fix confirmed **no change whatsoever**: all three still raise the identical 3+-causes `ValueError` from `assemble_investigation_evidence`, and still route through `assemble_investigation_evidence_for_benchmark` to the identical `PartialInvestigationEvidence` as before. The reason: `assemble_investigation_evidence`'s guard fires on cause *count* alone (`len(remaining_causes) > 2`, after decisions 10/12/18's suppression), a check performed entirely before `assemble_reconciliation_line_items`/`construct_corrected_query` is ever reached -- so a category's correctability was never a factor in how many causes survive suppression. This decision exists partly to record that a plausible-sounding causal link, once tested directly rather than assumed, did not hold.

**Proven, not asserted:** hand-verified against real `AMBIGUOUS_ATTRIBUTION` seed data (`test_filter_correction_matches_hand_verified_ambiguous_attribution_add_direction`, `tests/test_query_mutation.py`) -- the real, post-suppression `filter` finding mechanically corrects `24000.0` to `16500.0`, matching a hand-written equivalent query exactly. A defensive test confirms the function refuses to add a second predicate onto a column that already has one (a shape `_diff_filters`'s presence-only design should never produce as a real `filter` finding, but guarded against regardless).

**Explicit scope boundary:** the REMOVE direction remains a genuinely separate, unlocked design decision -- does "correcting toward no filter" mean dropping the predicate entirely (mirroring decision 5's zero-exclusion convention for `excluded_statuses`), or something else? `CASE_13_FILTER_EXCLUDED_STATUSES_COLLISION` still raises after this fix, unchanged in outcome, only in message text (`test_case_13_full_pipeline_now_raises_on_filter_alone_after_suppression`, `tests/test_investigation_evidence.py`, updated to match).

## 21. `apply_excluded_statuses_correction`'s zero-predicate ADD case, and a new same-fact collision it exposed

**Decision:** `apply_excluded_statuses_correction` gains a second valid case, mirroring decision 20's `apply_filter_correction` pattern exactly: when the side being corrected has ZERO existing status predicates and the target names one or more statuses to exclude, a new `NOT IN (...)`/`!=` predicate is constructed and added (via sqlglot's own `.where()` builder, AND-appending to an existing WHERE clause or creating one from scratch). The existing "exactly one predicate, rewrite or remove its values" path (Case 2, Case 4, Case 7, Case 13's own low-confidence suppression proof) is completely unchanged -- this is additive coverage for a previously-unconditional-raise case, not a redesign, and the multiple-predicates-still-ambiguous raise is untouched.

**Reasoning:** Closes the gap the Build 3 Day 2 Part 12 sweep named directly (`apply_excluded_statuses_correction requires exactly one status-filter predicate; found 0`), the mirror-image of decision 20's `filter`-ADD gap for the `excluded_statuses` field.

## 24. `apply_date_field_correction` was value-blind (column-only, not threshold-aware) -- a latent defect since Build 1, Day 6, now fixed

**Decision:** `apply_date_field_correction` (`src/query_mutation.py`) gains an optional `target_predicate` parameter. When given, it replaces the ENTIRE matched WHERE predicate leaf -- column AND comparison operator/threshold together -- with `target_predicate`, parsed via sqlglot. When omitted (the default), the function falls back exactly to its original Build 1, Day 6 behavior: only the bare column identifier is renamed in place, and the original threshold/operator are left untouched. `construct_corrected_query` (same module) gains a matching `other_side_sql` parameter: for a `date_field` `DefinitionDifference` correction where the caller has not manually overridden `target_value`, `other_side_sql` (the other source's real, uncorrected SQL) is parsed by a new helper, `_extract_date_predicate_snippet`, to pull the target column's actual filter predicate out of it, which is then passed to `apply_date_field_correction` as `target_predicate`. `src/reconciliation_assembly.py`'s `_single_cause_line_item` and `_shapley_pair_line_items` both gained a `source_b` parameter (previously only `source_a` was threaded through) specifically to supply this value at the one call site in the codebase that assembles real cross-source corrections.

The fallback preserves `SelfConsistencyIssue` date_field corrections unchanged and deliberately -- a self-consistency check compares a source only against its own declared definition, never against another source's real SQL, so there is no "other side" predicate to adopt in that case, and `other_side_sql` is never passed for it.

**Reasoning -- this was a latent defect, not a new one, and it was hiding in code this project has trusted since Build 1, Day 6:** `apply_date_field_correction`'s original column-only-swap has been exercised, unmodified, by every `date_field` correction this project has ever computed -- Case 1 (no `date_field` cause, unaffected), Case 3, and, once authored, `AMBIGUOUS_REVENUE_RECOGNITION`, `AMBIGUOUS_CUSTOMER_COUNTING`, and `AMBIGUOUS_ATTRIBUTION`. It was never actually correct in general: it silently assumed the corrected side's own existing threshold literal was also the right one to use post-correction, which is only true when both sides happen to already filter on the identical date value. For Case 3, `AMBIGUOUS_REVENUE_RECOGNITION`, and `AMBIGUOUS_ATTRIBUTION`, that assumption happened to hold -- both sides of each of those three fixtures use the identical literal cutoff (`'2024-01-01'`), differing only in which column they filter it on -- so the bug was present in the code but invisible in the output; their committed reconciliation figures were coincidentally correct, not proof the mechanism was sound.

The defect only became visible when a fixture's two sides used genuinely different threshold values: `AMBIGUOUS_CUSTOMER_COUNTING` (Build 3, Day 2, Part 7) declares `signup_date >= '2000-01-01'` on source_a (a permissive, effectively no-op cutoff -- "every customer who ever signed up") against `last_active_date >= '2024-01-01'` on source_b (a real, meaningful cutoff -- "active in the current period"). Correcting source_a's `date_field` column to `last_active_date` while silently keeping its own `'2000-01-01'` threshold produced a corrected query that still matched every row -- a silent no-op -- which is exactly why `date_field`'s attributed `dollar_impact` came out `-0.0` instead of a real, non-trivial figure, and why `AMBIGUOUS_CUSTOMER_COUNTING`'s `unexplained_residual` read `50.0` instead of `0.0` (Build 3, Day 3, Part 1, root-cause investigation). The defect was found by investigating a symptom (a non-zero residual on a two-cause fixture that should have reconciled exactly), not by an audit of `apply_date_field_correction` itself -- worth stating plainly, since it means this class of defect (a mechanically "successful," non-raising correction that is nonetheless silently wrong) does not announce itself the way a raised exception does, and a fixture whose numbers happen to still work out will not surface it.

**Proof, from this session's own verification, not asserted:**
- **Every call site of `construct_corrected_query` in the codebase was individually checked**, not inferred from the passing test count: the four call sites in `src/reconciliation_assembly.py` (`_single_cause_line_item`; `_shapley_pair_line_items`'s x_only/y_only/both) now pass `other_side_sql=source_b.sql`, correct in every case since the parameter is a no-op for anything other than a non-overridden `date_field` `DefinitionDifference`. `src/self_consistency.py`'s three call sites (`compute_self_consistency_dollar_impacts`'s own correction, and the suppressed-cause-folding function's two calls, one of which passes an explicit `target_value`) do not pass `other_side_sql` at all and are unaffected -- confirmed by `git diff` against the pre-fix commit showing `src/self_consistency.py` with zero lines changed, not by reasoning about it. Every `tests/test_query_mutation.py` call site that predates this fix (the aggregation test, the filter test, the two unsupported-category raise tests) also omits `other_side_sql` and is unaffected.
- **Before/after figures, all fixtures that exercise `date_field` correction, re-run individually, not just as part of the full suite:** Case 1 (no `date_field` cause -- unaffected, `300.0` before and after), Case 3 (`date_field=-400.0`/`excluded_statuses=500.0`, byte-identical before and after), Case 7 (no `date_field` cause -- unaffected, `200.0` before and after), `AMBIGUOUS_REVENUE_RECOGNITION` (`date_field=-1200.0`/`excluded_statuses=1150.0`, byte-identical), `AMBIGUOUS_ATTRIBUTION` (`date_field=-11500.0`/`excluded_statuses=11000.0`, byte-identical). **Only `AMBIGUOUS_CUSTOMER_COUNTING` changes:** `date_field` moves from `-0.0` to `100.0`, `excluded_statuses` moves from `100.0` to `50.0`, and `unexplained_residual` moves from `50.0` to `0.0` -- the corrected figures now sum to `known_gap` (`150.0`) exactly, closing the gap Build 3, Day 3, Part 1 root-caused rather than leaving it as an accepted artifact.
- Two new committed tests (`tests/test_query_mutation.py`) prove the fix directly against real seed data: `test_date_field_correction_with_target_predicate_adopts_real_threshold` (the old column-only swap really is a silent no-op, `450.0`; the threshold-aware correction matches a hand-written query, `300.0`) and `test_construct_corrected_query_other_side_sql_fixes_customer_counting_end_to_end` (same proof through the real dispatcher, not just the mutation function in isolation).

**Scope boundary, stated plainly:** this decision is specific to `date_field`. It does not touch, and does not claim to have improved, any of the following, still-open gaps: the `date_field`/`aggregation` `SQLStructuralDifference` categories' missing-`target_value` bug (decision 20's own scope note); `distinct`/`grouping`/`other`'s total lack of mutation coverage; or `apply_filter_correction`'s REMOVE-direction gap (decision 20). ## 26. `aggregation`-category structural/definitional collision: confirmed live, unresolved, and more dangerous than a crash

**Decision:** No suppression rule is written for this collision in this session. It is named, proven, and left explicitly unresolved -- inherited work for a future build, the same treatment decision 16 gave `late_arriving_data`.

**The collision, confirmed by direct execution (Build 3, Day 3, Part 4):** a plain `aggregation`-function difference between two sources (e.g. `SUM(amount)` vs. `COUNT(amount)`) is structurally guaranteed to also change the literal SQL text `sql_diff`'s own `_diff_aggregations` inspects -- there is no way to construct a genuine `aggregation` `DefinitionDifference` without the underlying SQL also differing in a way `_diff_aggregations` detects (confirmed directly: `_diff_aggregations` compares `(function, column)` per positional aggregate call and flags any mismatch; a real declared-aggregation difference is, by construction, also a real SQL-text difference in every case checked). Both findings -- `sql_diff`'s `aggregation` `SQLStructuralDifference` and `definition_diff`'s `aggregation` `DefinitionDifference` -- therefore survive `assemble_structural_and_definitional_evidence` side by side, with no suppression rule reconciling them, unlike `distinct` (decision 10) and `date_field` (decision 12), which both have one.

**The actual danger, stated precisely rather than left as "these are redundant":** the crash decision 25 documents only happens because this session's probe fixture *also* had two other real causes, pushing the total past the 3+-cause guard. That guard is a blunt, count-based check -- it has no way to know that two of the "causes" it's counting are actually one fact counted twice. **A scenario with an aggregation-function difference as its ONLY cause (no `date_field`/`excluded_statuses` difference at all) would land at exactly 2 remaining causes** (`aggregation`-definitional + `aggregation`-structural, both real, both surviving, both actually the same fact) **and would be silently fed into `shapley_pair_attribution` as if they were two genuinely independent, interacting causes** -- because the guard only checks `len(remaining_causes) > 2`, and 2 is not greater than 2. `shapley_pair_attribution` would run to completion, produce two dollar-impact figures that split one real fact's dollar value in half via marginal-contribution averaging (rather than attributing 100% of it to the one true cause), and `assemble_investigation_evidence` would return a normal-looking `InvestigationEvidence` with no exception, no warning, and a sum-check that still passes (the sum-check is an algebraic tautology of the averaging formula, decision 11/`shapley_pair_attribution`'s own docstring already states this -- it cannot catch a meaningless split between two views of one fact). **This is more dangerous than decision 25's crash, and is named as such explicitly:** a crash is loud, gets caught in review or by a test, and blocks a bad result from ever being reported; this collision, if it ever reaches a committed scenario, produces a plausible-looking, wrong dollar-impact split that nothing in this project's current test suite would flag, since no committed fixture has ever exercised this exact shape.

**Scope boundary, stated plainly -- not resolved here:** no suppression rule is designed or built in this decision. Any future scenario design, ambiguous or technical, that uses a genuine `aggregation`-function difference as one of its causes must first confirm whether it triggers this collision (it will, whenever the difference is a real function/column mismatch reaching both detectors unsuppressed) and must not be authored until a suppression rule exists and is proven against both a real-collision case and an over-fire case -- the same two-sided proof standard every prior suppression rule in this project received (decision 10's Case 2 proof + constructed over-fire test; decision 12's Case 3 proof + constructed over-fire test; decision 18/22's Case 13 proof + constructed over-fire tests). Designing that rule -- what "the same fact" means for two aggregation findings, and which one should survive (mirroring decision 10's own "business-declared beats mechanical" reasoning, or decision 18/22's confidence-dependent reversal) -- is real, separately-scoped work for a future build, not attempted here.

**Cross-reference -- this is the fourth confirmed instance of the same pattern, and the first one caught before it could corrupt a committed fixture:** decision 12's own pattern note already named this as recurring -- Day 4's self-consistency-vs-cross-source collision, decision 10's `distinct`-vs-`aggregation` collision, and decision 12's own `date_field`-vs-`date_field` collision, "each discovered only after further downstream work depended on the evidence being non-redundant." This `aggregation`-vs-`aggregation` collision is the fourth occurrence of that same shape (two independent tools' findings tracing to one fact, no suppression rule reconciling them) -- but unlike the first three, which were each found only after they had already shipped inside a committed fixture's relied-upon numbers (Case 4's precedence gap, Case 2's `distinct`/`aggregation` collision, Case 3's `date_field`/`date_field` collision), this one was found by a deliberate, targeted probe (Build 3, Day 3, Part 4's n>2 investigation) before any committed scenario ever exercised it. Decision 12's own forward note called for "a systematic audit of every `SQLStructuralDifference` category against every `DefinitionDifference` field for this same risk" before Build 3's larger scenario set was authored; that audit was never formally completed, but this session's probe happened to surface exactly the collision that audit would have been looking for, for the `aggregation` category specifically. `filter` (decisions 18/22) and `date_field` (decision 12) are now confirmed audited; `aggregation` is now confirmed to have a live, unresolved collision rather than merely being un-audited; `join_type` and `grouping`/`other` remain genuinely unaudited against this same risk.

**What this fixture was built to test, and what it actually found:** every 2-cause `excluded_statuses` pair committed before this session (Case 2, Case 3, and the three two-cause `AMBIGUOUS_*` scenarios) uses a *declared*, `confidence="high"` `excluded_statuses` side. Both sides deliberately filter the `status` column (source_a: a real `NOT IN` exclusion; source_b: an inclusion-style `status = 'active'` predicate `src.definition_diff._infer_excluded_statuses` does not recognize as an exclusion shape) specifically so `src.sql_diff._diff_filters`'s presence-only check never produces a `filter` finding at all -- confirmed live, this is the deliberate opposite of Case 13's "one side filters, the other doesn't" construction, and it works: no `filter` SQLStructuralDifference exists anywhere in this fixture's evidence, so decisions 18/22's filter/excluded_statuses suppression rule never has anything to fire against. `sql_diff`'s `date_field` finding does collide with `definition_diff`'s `date_field` finding (source_a's declared `order_date` vs. source_b's inferred `created_at`, `confidence="medium"` -- the same level decision 12's suppression has always been proven at), and decision 12 correctly suppresses it, leaving exactly `remaining_causes = [date_field, excluded_statuses]` -- 2, routing through `shapley_pair_attribution` as intended.

`assemble_investigation_evidence` runs to completion with no exception -- proving the Shapley-pair/correction machinery genuinely does execute with a low-confidence/inferred member, which was this fixture's actual design goal. But `unexplained_residual` is **650.0**, not `0.0`, against a `known_gap` of only `450.0` -- on a fixture with no data-quality cause, no third interacting cause, and no self-consistency issue, the exact shape every other clean two-cause fixture (Case 2, Case 3) reconciles to `0.0` exactly.

**Root cause, traced precisely:** `src.definition_diff._infer_excluded_statuses` returns the SAME fixed placeholder, `InferredField(value="(none)", confidence="low")`, for every low-confidence path -- zero status predicates, multiple status predicates, AND an unrecognized shape like `status = 'active'` (this fixture's own case). `"(none)"` is then parsed by `_parse_excluded_statuses_value` (`src/query_mutation.py`) to an empty list, and `apply_excluded_statuses_correction`'s zero-target branch (decision 20/21's own "corrected toward zero exclusions" convention) removes source_a's exclusion predicate ENTIRELY -- meaning "correct toward source_b's inferred value" actually means "include everyone," not "include only what source_b's real SQL includes." Source_b's real query is an INCLUSION filter (`status = 'active'`), a fundamentally narrower condition than "no filter at all" -- there is no vocabulary anywhere in this schema (`DeclaredDefinition.excluded_statuses` is exclusion-only by construction) to represent "correct toward including only X," so the correction machinery cannot reconstruct what source_b's SQL actually does whenever the source of low confidence is an inclusion-style predicate specifically (as opposed to zero or multiple predicates, where "(none)" may still be defensible). This is not new in kind -- Day 3's own documented tradeoff already named "`_infer_excluded_statuses` only recognizes `NOT IN`/`!=` exclusion-style predicates; an inclusion-style filter ... falls into the ... `"low"` confidence branch" as a benchmark-coverage gap -- but this is the first time that gap's actual DOLLAR consequence has been measured by running it through the full pipeline, and the consequence is large, not cosmetic.

**Why this is a genuinely different risk shape from decision 26's, not a repeat of it:** decision 26 (immediately above) is dangerous because a silent, wrong split can occur with NO signal anywhere that anything is amiss -- the sum-check still passes, nothing raises, nothing looks wrong. Here, the opposite is true: `unexplained_residual` correctly, loudly reports that something is unexplained (`650.0` is not a number a reader would mistake for "basically zero"). The individual `ReconciliationLineItem`s themselves (`date_field: 100.0`, `excluded_statuses: -300.0`) are exactly what a hand-reconstruction of the four Shapley counterfactual queries confirms -- the Shapley/reconciliation arithmetic is not wrong; the CORRECTION TARGET fed into it (`"(none)"`) does not describe what source_b's real SQL does. The residual is an honest, correctly-computed signal of a real representational gap, not a masked error -- which is exactly why this fixture is being kept and documented rather than discarded: `unexplained_residual` did its job.

**Proof, from real execution, not asserted:**
- `sql_diffs` on the raw (pre-suppression) pair contains exactly `{"date_field"}` -- no `filter` category present, confirmed directly (`test_case_14_both_sides_filtering_status_produces_no_filter_finding_at_all`, `tests/test_structural_definitional_precedence.py`).
- `definition_differences` (raw) is exactly `[("date_field", "medium"), ("excluded_statuses", "low")]`; after `assemble_structural_and_definitional_evidence`, `sql_differences == []` and both definitional findings survive (`test_case_14_date_field_suppressed_by_decision_12_leaving_exactly_two_causes`).
- `assemble_investigation_evidence` returns a real `InvestigationEvidence` (no exception), with `reconciliation` containing exactly two `shapley_pair_attribution`-computed line items (`date_field: 100.0`, `excluded_statuses: -300.0`) and `unexplained_residual == 650.0` against `known_gap == 450.0` (`test_case_14_full_pipeline_completes_with_a_real_but_large_residual`, `tests/test_investigation_evidence.py`). `reported_value_a` (`950.0`), `reported_value_b` (`500.0`), and `known_gap` (`450.0`) are real execution figures against this fixture's own seed data (`scripts/build_seed_data.py`), per decision 13's calibration convention.

**Scope boundary, stated plainly -- not resolved here:** no fix to `_infer_excluded_statuses`, `apply_excluded_statuses_correction`, or the schema's excluded_statuses vocabulary is attempted in this decision. `CASE_14_DATE_FIELD_LOW_CONFIDENCE_EXCLUDED_STATUSES` stays out of `SCENARIOS` until a future session decides how to represent this honestly -- either (a) accept the residual as a documented, structural consequence of low-confidence inference and add the fixture to `SCENARIOS` with that caveat stated explicitly (the same shape of caveat Cases 8-11's own `SCENARIOS` entry already carries, for a different reason), or (b) extend the inference/correction layer to distinguish "genuinely zero/ambiguous predicates" from "a real but unrepresentable inclusion-style predicate" before trusting this fixture's residual in any full-`SCENARIOS` sweep. Not a schema change to `DeclaredDefinition` itself (that would be the same category of work decision 23 already ruled out of scope for Build 3 when it closed the ambiguous-scenario set) -- whatever fix is chosen belongs in the inference/correction layer, not the declared vocabulary.

**This is a bug in `_infer_excluded_statuses`/`apply_excluded_statuses_correction` themselves, not a defect confined to Case 14 -- excluding Case 14 from `SCENARIOS` protects nothing beyond Case 14.** Stated explicitly because the natural mis-reading of the paragraph above is "the problem was scoped to a fixture and the fixture was excluded, so it's contained." It is not: any future scenario, technical or ambiguous, whose low-confidence side has a genuinely inclusion-shaped status predicate (`status = 'active'`, `status IN (...)` as an inclusion set, or any shape other than a recognized `NOT IN`/`!=` exclusion) will silently reproduce the identical failure the moment it reaches a Shapley pair or single-cause correction on that field -- `unexplained_residual` will be large and real, not flagged by any existing test, dispatch table, or suppression rule, because nothing in this codebase currently distinguishes "confidence is low because the predicate is genuinely ambiguous (zero/multiple matches)" from "confidence is low because the predicate is a real, well-formed inclusion filter this schema just can't name." A future scenario author who does not know this decision exists has no code-level guard stopping them from authoring exactly this shape and adding it straight to `SCENARIOS`. See the corresponding CONTEXT.md Open Items entry, reworded to state this as a standing risk for any future inferred-`excluded_statuses` scenario, not merely "Case 14 is excluded."

## 30. Residual-framing self-contradiction, observed and characterized for Build 3's unsupported-claim-rate checker (not fixed -- deliberately left as a test target)

**Decision:** A third real, observed defect in the Hugging Face explainer's prose is recorded here, matching decision 14's own standard of specificity -- enough reproduction detail that whoever builds Build 3's unsupported-claim-rate checker can write a targeted test for this exact pattern, not a vague "check for hallucination" mandate.

**What was tested:** Build 3, Day 4, Part 1 added a `data_quality_issues`-rendering section to `_format_evidence_prompt` (`src/explainer.py`) plus prompt instructions covering decisions 14 and 17's named risks (never sum a `data_quality_issues` figure against a `reconciliation` figure; never describe an investigation as "no cause found" when `data_quality_issues` is populated but `reconciliation` is empty). Live verification of those two instructions passed cleanly on all 5 tested cases. Build 3, Day 4, Part 2 added a third instruction, on the same live-verification pass, addressing a defect that surfaced despite the first two working: the model characterized every data-quality cause as only "partially" explaining the gap, reasoning from `unexplained_residual`'s nonzero value even where a `data_quality_issues` figure fully accounts for it (this project's own additive-only accounting convention, Build 2 Day 5, means `unexplained_residual` never folds in `data_quality_issues`, but the prompt did not say so). The new instruction states plainly that a nonzero residual is not evidence a data-quality cause is incomplete, and instructs the model to discuss the residual only as a separate fact about what the reconciled causes do not cover. Re-verified live (real Hugging Face API calls) against Cases 8, 9, 10, 11, and 20 with the new instruction in place.

**The defect, precisely -- per-case breakdown, not averaged into a single "partially works" statement:**

- **Case 8 (`case_08_stale_extract`) -- clean pass.** *"This data-quality issue accounts for the entire gap, and we have a confirmed cause for the discrepancy. [...] The unexplained residual is -$150.00, which is a separate fact from the reconciled cause. It does not indicate the existence of other causes or the need for further investigation. - **Case 9 (`case_09_missing_partition`) -- borderline: confusing wording, but not factually wrong.** *"The unexplained residual figure is -$250.00. - **Case 10 (`case_10_referential_integrity`) -- FAIL, genuine self-contradiction within one response.** Paragraph 2: *"This data-quality issue is a complete and confirmed finding, and we can say that it accounts for a portion of the gap. - **Case 11 (`case_11_referential_integrity_source_b`) -- FAIL, same self-contradiction pattern.** Paragraph 3: *"The data-quality issue is a complete and confirmed finding in its own right, and we should not assume that other causes may exist or that further investigation is needed."* Paragraph 4, the closing summary: *"In summary, while we have identified a data-quality issue that contributes to the discrepancy, the entire gap remains unexplained, and the residual figure of -$300.00 indicates that further investigation is needed to fully understand the causes of the discrepancy."* Correct instruction-following in paragraph 3 is directly reversed in paragraph 4.

- **Case 20 (`case_20_stale_extract_join_collision`) -- FAIL on this instruction specifically; decision 17's conflation check (Build 3, Day 4, Part 1) still PASSES.** Closing paragraph: *"Despite these confirmed causes, the residual gap is not zero. **Consequence:** this pattern is a real, concrete candidate for what Build 3's future unsupported-claim-rate checker (decision 5's ≤10% gate) should detect -- a response that states a correct constraint in one paragraph and violates it in another paragraph of the same output is a specific, checkable shape (search the full response text for both a correctly-scoped statement matching the instruction's own claim and a contradicting "portion of the gap" / "other factors" / "other causes may exist" / "further investigation is needed" phrase co-occurring), not a vague hallucination mandate -- matching decision 14's own stated standard for actionable findings.

## 31. Evidence-only escalation instruction: probed and found not viable at this evidence granularity -- a closed negative finding, not an attempted fix

**Decision:** This entry closes off a specific, tested approach to evidence-only escalation recognition. It does not propose or attempt a fix -- the underlying design question (how should this project's explainer recognize genuine business-rule ambiguity, if not this way) is named as an open fork below, not resolved here.

**What was tested (Build 3, Day 4, Part 4, PR #128):** an unconditional instruction added to `_format_evidence_prompt` (`src/explainer.py`), not gated by any Python-computed eligibility check and with no access to `BenchmarkEntry.is_ambiguous` or any other ambiguity label -- the model was asked to recognize genuine policy ambiguity from the rendered evidence content alone. The instruction's locked trigger: escalate (produce a single fixed `ESCALATION_STATEMENT`, verbatim, with no accompanying explanation) only when `definition_differences` shows two or more entries that are all `source="declared"`, all `confidence="high"`, with no data-quality or self-consistency signal pointing to a mechanical error instead. The instruction explicitly warned against escalating merely because confidence is low or reconciliation is incomplete (`PartialInvestigationEvidence`) -- those situations call for stating uncertainty, not escalation.

**The result, precisely, per case -- not averaged into a single pass/fail:**

- **False-escalation probe, 2/2 correct (no false positives):** `CASE_2_MULTI_CAUSE` (`excluded_statuses` + `aggregation`, both declared/high -- a genuinely risky shape that does NOT warrant escalation) and `CASE_19_DATE_FIELD_EXCLUDED_STATUSES_DECLARED` (`date_field` + `excluded_statuses`, both declared/high, this project's own item 5 of the finalized 8-scenario list) both produced normal explanations, never the escalation statement.
- **True-escalation probe, 0/2 on the genuinely-qualifying cases (a decisive, not marginal, miss):** `AMBIGUOUS_REVENUE_RECOGNITION` (`InvestigationEvidence`, `date_field` + `excluded_statuses`, both declared/high -- genuinely meets the locked criteria) and a synthetic `is_ambiguous=True` probe scenario constructed to reach `PartialInvestigationEvidence` (no committed ambiguous `BenchmarkEntry` currently routes there -- confirmed live before assuming otherwise, all 6 now complete directly per decision 22's own ripple effect) both produced normal explanations of the findings. **The escalation statement was never produced, verbatim or in any form, in any of the 5 live calls made across the entire probe.**

**The structural gap, named explicitly, not just a model-compliance failure:** the locked "two or more declared, high-confidence differences" criteria cannot, by construction, ever trigger correctly on a single-cause ambiguous scenario. `AMBIGUOUS_REFUND_TIMING` (this project's own Pattern 1: single `date_field` `DefinitionDifference` only) correctly did not escalate under this instruction -- but only because it structurally cannot meet a "two or more" threshold, not because the model judged the business question itself. Cause COUNT was doing the discriminating work in this criteria's design, and a single-cause scenario has no other structural signal in the evidence to distinguish "legitimate policy choice" from "ordinary bug" -- both look identical in shape (one `DefinitionDifference`, declared, high confidence) regardless of which is actually true. This matters beyond this one fixture: even a hypothetical future version of this instruction that achieved perfect recall on multi-cause cases would still structurally fail Pattern-1 coverage entirely -- and Pattern 1 (`AMBIGUOUS_REFUND_TIMING`, `AMBIGUOUS_CURRENCY_TIMING`) was deliberately built into the ambiguous scenario set (decision 23) specifically to keep escalation-recall non-gameable by a system that only ever looks for multi-cause collisions. A "two or more differences" criteria is therefore not a narrow-but-fixable starting point -- it is structurally blind to an entire category this project's own benchmark was designed to test.

**What this is, and isn't:** this is judged a genuine, informative negative result -- concrete evidence that a single unconditional instruction, evaluated once without iterative prompt-tuning (deliberately, to avoid overfitting to these exact five fixtures, the same discipline decisions 14 and 30 already established), does not achieve usable recall against `meta-llama/Llama-3.1-8B-Instruct` at this evidence granularity. It is NOT proof that evidence-only escalation recognition is impossible in general -- a different instruction shape, a different evidence granularity, or a different model might behave differently, none of which this single probe tested or rules out.

**Open fork, stated plainly, not resolved here:** whether to (a) continue refining evidence-only recognition -- a different criteria, additional evidence signals, or a differently-structured instruction -- or (b) use a structurally different mechanism entirely, for example a model self-report of confidence or uncertainty produced as a distinct step before the model commits to an answer, rather than a single-shot classify-and-respond instruction folded into the same generation as the explanation itself. This is the next real design decision for this feature area, unresolved by this entry.

**What this decision does NOT do:** no new instruction attempt, no prompt-wording iteration beyond PR #128's single honest attempt, no resolution of the open fork above, no changes to `BenchmarkEntry`, the wrapper, or any scoring code, and no code changes of any kind -- this entry only records PR #128's already-shipped, already-tested result.
